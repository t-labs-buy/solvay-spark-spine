Deploying the app to the ivolve cloud server

A step-by-step guide to packaging Solvay Spark Spine AI as a container image, publishing it to the ivolve registry and running it on the AWS EC2 server — written for someone who has never done any of this before. Every command comes with what it does and why it is there.

Audience — new team members, no container experience assumed Needs first — a Mac with the repository, the server key, a registry token Server — AWS EC2, Ubuntu, 13.204.129.141 Registry — reg.ivolve.cloud/ivolve/solvay-spark-spine
The deployment
Read this first

The big picture: what we built and how the pieces fit

Solvay Spark Spine AI is a web application. It converts Solvay's SPARK programme documents to text, answers questions about them, draws a knowledge graph of processes, systems and specifications, and runs AI agents on top. On a developer's Mac it runs straight from the source code. On the server it runs as a set of containers.

Deploying it means moving the application from your Mac to the server. That happens in three places:

Your Mac
Build
  1. Package the code into an image.
  2. Export the database.
  3. Hold the corpus files.
push image
Registry
reg.ivolve.cloud Stores the image, like a library shelf, so the server can fetch it.
pull image
AWS EC2 server
Runs the stack
  1. The app (port 8030).
  2. Postgres + pgvector (the database).
  3. Ollama (turns text into vectors).
  4. Neo4j (the graph database).
  5. Hindsight (the agent's memory).

The corpus files and the database export don't go through the registry. They are client data, so you copy them from your Mac straight to the server over SSH.

Words you will meet

Image A packaged, read-only snapshot of the app: the code, the Python libraries and the tools it needs (LibreOffice, Tesseract). Built once, run anywhere.
Container A running copy of an image. Stopping or deleting a container doesn't delete the image.
Registry A server that stores images. Ours is reg.ivolve.cloud (GitLab). You push images to it and pull them from it.
Docker / Podman The programs that build and run containers. On the Mac, docker is actually Podman; the server runs real Docker. The commands are the same.
Docker Compose Starts several containers together from one file, compose.yml, so you don't start each one by hand.
Volume A storage area that outlives the container. The database lives in a volume, so updating the app doesn't wipe the data.
SSH and the .pem key SSH is how you get a terminal on the server. The .pem file is your key; without it the server won't let you in.
SSH tunnel Forwards a port on your Mac to a port on the server, so http://localhost:8030 in your browser reaches the app on the server.
How to read this guide

Sections 1–9 are the first-time deployment, in the order you do it. Sections 10–11 are what you do afterwards, day to day. Section 12 is troubleshooting, and section 13 covers security and what isn't included. Every code block has a copy button. Each block says whether it runs on your Mac or on the server; running a command on the wrong machine is the most common beginner mistake.

2Convert a .ppk key to .pem (only if you were given a .ppk)

brew install putty

Dockerfile: the recipe for the image

Purpose. A Dockerfile is a list of instructions that turns the source code into an image. Ours builds in four stages. Each stage does one job, and only the last one becomes the final image, so build tools and caches don't bloat it.

StageWhat it doesWhy it is done this way
ui Starts from a Node.js image, runs npm ci and npm run build on frontend/, and produces the web pages in static/dist. It runs on your Mac's own chip, not in emulation: the output is plain HTML/JS/CSS, the same on every computer, and emulation made this step hang.
models Installs Docling and downloads its AI models (page layout, tables, OCR) into /opt/docling-models. Also native: running the model code in emulation crashed. The model files work on any computer, and pre-downloading them means the server never fetches them at runtime.
deps Installs compilers, then the CPU-only version of PyTorch, then every library in requirements.txt, pinned by constraints.txt. CPU-only PyTorch avoids several GB of GPU code the server can't use. Compilers are needed for tesserocr but stay out of the final image.
runtime (final) A clean Python image plus LibreOffice, Poppler, Tesseract, WeasyPrint's libraries and OpenCV's libraries. It copies in the Python libraries, the models, the app code (backend/, docs/, data/) and the built UI. These are the programs the app runs: LibreOffice renders documents, Poppler splits PDFs into pages, Tesseract reads text from images.

The final stage also sets how the container behaves when it runs:

InstructionWhat it means
USER appThe app runs as an ordinary user (id 1000), not as the administrator. That's safer if the app is ever compromised.
ENV DOCLING_ARTIFACTS_PATH=/opt/docling-modelsTells Docling to use the models built into the image.
EXPOSE 8000Inside the container the app listens on port 8000. compose.yml maps it to 8030 on the server.
HEALTHCHECK … /api/healthEvery 30 seconds Docker asks the app "are you OK?" and marks the container healthy or unhealthy.
CMD ["uvicorn", "backend.api.app:app", "--host", "0.0.0.0", …]The command that starts the web server when the container starts.

Dockerfile.hindsight: the memory server's image

Purpose. Hindsight is the Evidence Agent's long-term memory: after each investigation it files what was found, and before the next one it recalls what is relevant. It is a separate server with its own image, because its libraries conflict with Docling's: installing both together would downgrade the document converter.

StageWhat it doesWhy it is done this way
models Downloads two small models: BAAI/bge-small-en-v1.5 (turns memories into vectors) and cross-encoder/ms-marco-MiniLM-L-6-v2 (ranks recalled memories). Runs natively on your Mac, like the app's model stage. The files are the same on every computer.
runtime (final) Installs CPU-only PyTorch and hindsight-api==0.10.1, copies in the models, and runs hindsight-api on port 8888 as user app. Version 0.10.1 is pinned to match the Mac setup. HF_HUB_OFFLINE=1 makes it use the bundled models without checking the internet.

It keeps no data inside the container: the memories live in a hindsight database in the stack's Postgres, so they survive updates and restarts.

.dockerignore and constraints.txt: the supporting files

.dockerignore lists what the build must never see: .env (passwords), backup/ (database dumps), solvay-spark/ and knowledge_base/ (client data), the virtual environments and node_modules. It shrinks what the build reads from about 5 GB to about 15 MB. It also means anyone who can pull the image can't read secrets or Solvay's documents from it.

constraints.txt pins the exact version of about 200 Python libraries. requirements.txt names the libraries but not their versions, so without this file two builds an hour apart could get different versions. That happened: the build broke when PyPI was slow and pip fell back to a 2018 version of a library.

If you change requirements.txt

constraints.txt must be refreshed too, or the new library may fail to install. How to do it is written at the top of constraints.txt.

compose.yml: the whole stack in one file

Purpose. compose.yml describes every container the server runs, how they connect, what storage each gets and what settings they receive. docker compose up -d reads it and starts everything, in the right order.

ServiceImageWhat it does and key settings
app reg.ivolve.cloud/ivolve/solvay-spark-spine:latest The application. Reads .env and is told where the others are (DATABASE_URL, OLLAMA_HOST, NEO4J_URI). Published on ${APP_PORT}; on our server that's 127.0.0.1:8030, reachable only from the server itself. Starts only after Postgres and Neo4j report healthy.
postgres pgvector/pgvector:pg18 The database: user spark, database solvay, password from POSTGRES_PASSWORD. Holds the search index and run history. No port is published, so only the other containers can reach it.
ollama ollama/ollama Runs the bge-m3 embedding model, which turns questions into vectors for search.
ollama-pull ollama/ollama A one-off helper that downloads bge-m3 into Ollama, then exits. Seeing it as Exited is normal.
neo4j neo4j:5-community The graph database behind the Cypher view. User neo4j, password from NEO4J_PASSWORD. The app loads the knowledge graph into it at startup.
hindsight-db pgvector/pgvector:pg18 A one-off helper that waits for Postgres, creates the hindsight database if it is missing, then exits. Seeing it as Exited is normal.
hindsight reg.ivolve.cloud/ivolve/solvay-spark-spine-hindsight:latest The memory server, on port 8888 inside the stack. Uses ANTHROPIC_API_KEY from .env: Claude Opus reads each investigation and files its facts; Claude Sonnet answers "Ask memory". The app finds it at HINDSIGHT_URL=http://hindsight:8888.

scripts/docker-publish.sh: build and push in one command

Purpose. Builds the image for the server's type of processor and uploads it to the registry, so you don't have to remember a long build command. Run it bare for the app, or as ./scripts/docker-publish.sh hindsight for the memory server. Its instructions, in order:

  1. Moves to the repository root, so it works from any folder.
  2. Picks the recipe and name: Dockerfile → reg.ivolve.cloud/ivolve/solvay-spark-spine, or with hindsight, Dockerfile.hindsight → …/solvay-spark-spine-hindsight. Anything else prints the usage and stops.
  3. Sets the tag to the current git commit (e.g. 7dbac01).
  4. Warns about uncommitted changes. They're still built in, but the tag then doesn't describe exactly what's inside.
  5. Builds for linux/amd64, the server's processor type. Your Mac is ARM, so this part runs under emulation and is slower.
  6. Uses Podman (podman build --format docker) when Docker's buildx isn't available, which is the case on our Macs. --format docker keeps the healthcheck, which Podman's default format drops.
  7. Pushes two tags: :<commit>, a fixed version you can go back to, and :latest, what the server pulls by default.

scripts/db-export.sh: save the database to a file

Purpose. The server's Postgres starts empty. This script saves your local database (the search index with all its embeddings, and the run history) into one file you can copy to the server and restore. Its instructions, in order:

  1. Reads DATABASE_URL from your environment or from .env. If it isn't set, it stops with an error.
  2. Creates backup/ if it doesn't exist. git ignores that folder, so dumps are never committed.
  3. Runs pg_dump --format=custom --no-owner --no-acl: a compressed dump, without your local user names and permissions, so it restores cleanly under the server's spark user.
  4. Names the file backup/spark-<date>.dump and prints its size.
Why the database name doesn't matter

Your local database is called docling; the server's is called solvay. That's fine: a dump holds the contents, not the name, and the restore command decides where they go (-d solvay).

Step 3 · On your Mac

Build the image and push it to the registry

Where — your Mac, in the repository folder Needs first — a registry token with write_registry
1Commit your changes
cd ~/Programme/solvay-spark-spine
git status
git add -A
git commit -m "Describe your change"

git status shows what changed; git add -A stages everything; git commit records it. Committing first means the image's tag (the commit id) describes exactly what's inside.

2Log in to the registry
podman login reg.ivolve.cloud

Asks for a username (your GitLab username) and a password (paste the token, not your GitLab password). Podman remembers it, so you only log in again when it expires.

3Build and push
./scripts/docker-publish.sh

Runs the publish script described in step 2. The first build takes 20–40 minutes; later builds reuse unchanged layers and take a few minutes. It ends with: 

Pushed reg.ivolve.cloud/ivolve/solvay-spark-spine:7dbac01 and reg.ivolve.cloud/ivolve/solvay-spark-spine:latest
4Build and push the memory server (first time, then only when it changes)
./scripts/docker-publish.sh hindsight

Builds Dockerfile.hindsight and pushes solvay-spark-spine-hindsight. It rarely changes, so after the first time, run it only when Dockerfile.hindsight does.

Why the push can be slow

The image is about 4.5 GB. Layers the registry already has are skipped (Blob … skipped: already exists), but Podman still checks and compresses each one first. Only the layers that changed, usually the app code, are actually uploaded.

What you have now

The image is in the registry. Check it at reg.ivolve.cloud/ivolve/-/packages: solvay-spark-spine should list latest and the commit tag.

Step 6 · On your Mac

Copy the files to the server

Where — your Mac, in a new terminal (not the SSH one)

Four things go to the server: compose.yml, .env.example, the database dump, and the two data folders (solvay-spark/ and knowledge_base/). They all go into ~/solvay-spark-spine on the server. 

cd ~/Programme/solvay-spark-spine

ssh -i ~/Downloads/ivolve-cloud-server.pem ubuntu@13.204.129.141 'mkdir -p ~/solvay-spark-spine'

scp -i ~/Downloads/ivolve-cloud-server.pem compose.yml .env.example backup/spark-2026-09-29.dump ubuntu@13.204.129.141:~/solvay-spark-spine/

rsync -avz -e "ssh -i ~/Downloads/ivolve-cloud-server.pem" solvay-spark/ ubuntu@13.204.129.141:~/solvay-spark-spine/solvay-spark/

rsync -avz -e "ssh -i ~/Downloads/ivolve-cloud-server.pem" knowledge_base/ ubuntu@13.204.129.141:~/solvay-spark-spine/knowledge_base/
CommandWhat it does
cd ~/Programme/solvay-spark-spineMoves into the project on your Mac, so the file names below are found.
ssh … 'mkdir -p ~/solvay-spark-spine'Runs one command on the server without staying logged in: creates the project folder. -p means no error if it exists.
scp … compose.yml .env.example backup/…dump ubuntu@…:~/solvay-spark-spine/"Secure copy": copies the three files to the server's project folder.
rsync -avz -e "ssh -i …" solvay-spark/ …Copies the 609 MB corpus folder. -a keeps subfolders and dates, -v lists files, -z compresses in transit. Run again, it copies only what changed.
rsync … knowledge_base/ …Copies the knowledge base the same way. Don't skip it: without it the knowledge graph shows 370 BPML processes instead of 1976.
The trailing slash matters

solvay-spark/ with a slash means "the contents of this folder". Without it, rsync creates solvay-spark/solvay-spark/ on the server and the app finds nothing.

Copying additional files later

Same pattern: scp for single files, rsync for folders.

# One file, e.g. a new document into the knowledge base
scp -i ~/Downloads/ivolve-cloud-server.pem "knowledge_base/New document.md" ubuntu@13.204.129.141:~/solvay-spark-spine/knowledge_base/

# A whole folder, sending only what changed
rsync -avz -e "ssh -i ~/Downloads/ivolve-cloud-server.pem" solvay-spark/ ubuntu@13.204.129.141:~/solvay-spark-spine/solvay-spark/

# Preview what rsync would copy, without copying
rsync -avzn -e "ssh -i ~/Downloads/ivolve-cloud-server.pem" solvay-spark/ ubuntu@13.204.129.141:~/solvay-spark-spine/solvay-spark/

Put quotes around file names with spaces. -n is a "dry run": it lists what would change and copies nothing. After copying new corpus or knowledge-base files, rebuild the knowledge graph (section 11).

What you have now

Step 7 · On the server

Configure the settings file (.env)

Where — the server, logged in with SSH Needs first — the Anthropic API key

.env holds the server's settings and passwords. It is created from the template and never leaves the server. 

cd ~/solvay-spark-spine
cp .env.example .env
echo 'APP_PORT=127.0.0.1:8030' >> .env
openssl rand -hex 24
nano .env
CommandWhat it does
cp .env.example .envCopies the template to the real settings file.
echo 'APP_PORT=127.0.0.1:8030' >> .envAppends a line (>> adds; > would overwrite the file). The app then listens on port 8030, reachable from the server only. Port 8000 is taken by another team's app on this shared server.
openssl rand -hex 24Prints a strong random password. Run it once for each secret you need.
nano .envOpens the file in a simple editor. Save with Ctrl+O, Enter; exit with Ctrl+X.

Fill in at least these:

SettingValue
ANTHROPIC_API_KEYThe team's Anthropic key.
POSTGRES_PASSWORDA generated password. It becomes the password of the database user spark.
NEO4J_PASSWORDA generated password, at least 8 characters; Neo4j refuses shorter ones.
APP_USERNAME / APP_PASSWORDThe login people type on the app's sign-in page. Choose them; don't leave the default test/test.
APP_SECRET / DEMO_SECRETGenerated values. Without them, every restart signs everyone out.
DEMO_USERNAME / DEMO_PASSWORDThe Demo Mode login. Change the default solvay/solvay.
Database and graph usernames are already set

compose.yml fixes the Postgres user (spark), the database (solvay) and the Neo4j user (neo4j). You only choose the passwords.

Set the passwords before the first start

Postgres and Neo4j read their passwords only when they first create their data. Change a password later and they keep the old one. The fix is to delete their volume and start again (see troubleshooting).

Step 8 · On the server

Start the app on the server

Where — the server, in ~/solvay-spark-spine Order — services, then restore, then app 
cd ~/solvay-spark-spine
docker login reg.ivolve.cloud
docker compose pull
docker compose up -d postgres ollama ollama-pull neo4j
docker compose ps
docker compose exec -T postgres pg_restore -U spark -d solvay --no-owner --no-acl < spark-2026-09-29.dump

CommandWhat it does
docker login reg.ivolve.cloudLogs the server in to the registry, so it may download the image. A token with read_registry is enough.
docker compose pullDownloads every image named in compose.yml.
docker compose up -d postgres ollama ollama-pull neo4jStarts the supporting services in the background (-d, "detached"). The app waits until the database is restored.

A healthy answer looks like this:

{"ok":true,"preview_available":true,"soffice":"/usr/bin/soffice","pdftoppm":"/usr/bin/pdftoppm"}
Harmless messages

WARN No services to build from compose is normal. So is a pg_restore warning that extension "vector" already exists. ollama-pull and hindsight-db showing Exited is normal: they finished their one job.

What you have now

The whole stack runs on the server. It keeps running after you log out, restarts by itself if a container crashes, and comes back after a reboot (restart: unless-stopped plus systemctl enable docker).

Step 9 · On your Mac

Open the app in your browser

The app accepts connections from the server itself only, so it isn't on the public internet. You reach it through an SSH tunnel. On your Mac: 

ssh -i ~/Downloads/ivolve-cloud-server.pem -N -o ServerAliveInterval=60 -L 8030:localhost:8030 ubuntu@13.204.129.141
PartMeaning
-L 8030:localhost:8030Port 8030 on your Mac forwards to port 8030 on the server. The first number is your Mac's side; change it if 8030 is busy on your Mac (e.g. -L 8031:localhost:8030).
-NOpens only the tunnel, no terminal. The window looks frozen; that's correct.
-o ServerAliveInterval=60Sends a small signal every minute, so an idle tunnel isn't dropped.

Leave that window open and browse to http://localhost:8030. Sign in with APP_USERNAME / APP_PASSWORD from the server's .env. Close the window (or Ctrl+C) to close the tunnel; the app keeps running on the server.

A tunnel that reconnects by itself

Install autossh (brew install autossh) and run autossh -M 0 -f -N -o ServerAliveInterval=60 -o ServerAliveCountMax=3 -i ~/Downloads/ivolve-cloud-server.pem -L 8030:localhost:8030 ubuntu@13.204.129.141. It runs in the background and reopens the tunnel whenever it drops.

Check every part works

  1. Ask tab — ask a question. An answer with cited excerpts proves Postgres, Ollama and the Anthropic key all work.
  2. Knowledge Graph — counts should match your Mac: 217 documents, 1976 BPML processes, 165 specifications.
  3. Cypher view — a query runs, so Neo4j works.
  4. Evidence Agent — the memory indicator shows as available, so Hindsight works. After a finished investigation, Ask memory can answer from it.
  5. Convert a document — a small PPTX or PDF converts, so LibreOffice, Tesseract and Docling work.
What you have now

The app, deployed and verified. The rest of this guide is running it day to day.

Day to day · On the server

Check the app is running

From the project folder

cd ~/solvay-spark-spine
docker compose ps
curl localhost:8030/api/health
docker compose logs --tail 50 app
CommandWhat it tells you
docker compose psEach service's state. All should be Up; app, postgres, neo4j and hindsight also (healthy). ollama-pull and hindsight-db show Exited; that's correct.
curl localhost:8030/api/healthWhether the app answers. Expect {"ok":true,…}.
docker compose logs --tail 50 appThe app's last 50 log lines: errors show up here. Use -f instead of --tail 50 to follow live; Ctrl+C stops following.

From any folder

docker ps --filter name=solvay-spark-spine
docker compose -p solvay-spark-spine ps
docker logs --tail 50 solvay-spark-spine-app-1
docker stats --no-stream

docker ps --filter lists the stack's containers from anywhere. -p solvay-spark-spine names the compose project, so compose commands work outside the folder. docker stats shows each container's CPU and memory use.

Restart or stop

cd ~/solvay-spark-spine
docker compose restart app
docker compose down
docker compose up -d

restart app restarts just the app. down stops and removes every container; the volumes, and so the data, are kept. up -d starts everything again.

Never add -v to down unless you mean it

docker compose down -v also deletes the volumes: the database, the graph and the models. You'd have to restore the dump again.

On your Mac:

cd ~/Programme/solvay-spark-spine
git add -A && git commit -m "Describe your change"
./scripts/docker-publish.sh

Then on the server:

cd ~/solvay-spark-spine
docker compose pull app
docker compose up -d app
curl localhost:8030/api/health

pull app downloads the new latest image; up -d app replaces the running app container with one from the new image. The database and files are untouched.

Rolling back

Every push also has a commit tag. To go back to an earlier version, add TAG=7dbac01 (the commit you want) to the server's .env, then run docker compose up -d app. Remove the line to follow latest again.

After changing Dockerfile.hindsight

On your Mac, ./scripts/docker-publish.sh hindsight. Then on the server:

cd ~/solvay-spark-spine
docker compose pull hindsight
docker compose up -d hindsight

The memories are in the database, so they survive the update.

After changing compose.yml

scp -i ~/Downloads/ivolve-cloud-server.pem compose.yml ubuntu@13.204.129.141:~/solvay-spark-spine/

On your Mac. Then on the server, docker compose up -d applies it.

Rebuild the knowledge graph

After copying new corpus or knowledge-base files (section 6), rebuild the graph on the server: 

curl -s -X POST localhost:8030/api/graph/rebuild >/dev/null
PartMeaning
curlSends a web request from the command line.
-sSilent: no progress bar.
-X POSTA POST request, which tells the app to do something rather than just return data.
localhost:8030/api/graph/rebuildThe app's endpoint that rebuilds the graph from solvay-spark/*/markdown, knowledge_base/ and the database, then refreshes Neo4j.
>/dev/nullThrows away the reply, which is the whole graph and very long. Leave it off, or use | head -c 300, to see the start.

It takes a few seconds. Then reload the Knowledge Graph page and compare the counts with your Mac. The app also rebuilds by itself when it notices its inputs changed, but running this makes it happen now.

New documents need indexing too

The graph rebuild doesn't add documents to the Ask search index. For many new documents, the simplest route is to index them on your Mac, then export and restore the database again (sections 4 and 8).

When things go wrong

Troubleshooting

The problems below all happened during the first deployment, with the fix that worked.

Logging in and copying

ssh says "Connection timed out".

The server's firewall isn't letting you in. In the AWS console: EC2 → the instance → Security tab → its security group → Edit inbound rules → add SSH, port 22, source My IP. Your IP changes when you change networks, so you may need to update it.

ssh says "Permission denied (publickey)".

Wrong key or wrong user. Check the path after -i is the right .pem, and that the user is ubuntu. A converted .ppk must use -O private-openssh-new.

ssh says "UNPROTECTED PRIVATE KEY FILE".

Run chmod 400 ~/Downloads/ivolve-cloud-server.pem. Check the file name in chmod matches the one in ssh.

scp or rsync says "No such file or directory".

You're not in the project folder on your Mac, or the dump's name is different. Run cd ~/Programme/solvay-spark-spine and ls backup/ to see the real dump name.

Building and pushing

The build hangs for a long time on one step, or dies with "Killed".

The Podman VM is out of memory. Give it 8 GB (section 1, step 1) and stop other local containers.

The build fails with "Read timed out" from pypi.org.

A slow network. Run ./scripts/docker-publish.sh again: finished layers are cached, and pip already retries 10 times with a 2-minute timeout.

The push fails with "unauthorized" or "denied".

Log in again with podman login reg.ivolve.cloud, using a token that has write_registry.

Starting on the server

"Bind for 127.0.0.1:8000 failed: port is already allocated".

Another app uses that port. Find out which:

docker ps --format '{{.Names}}\t{{.Ports}}' | grep 8000
sudo ss -ltnp | grep ':8000'

On our shared server it was another team's container, which must not be stopped. Set a free port in .env (APP_PORT=127.0.0.1:8030) and run docker compose up -d app.

"dependency failed to start: container …-neo4j-1 is unhealthy".

Look at Neo4j's log first:

docker compose logs --tail 50 neo4j

Usually the password is under 8 characters, or it changed after the first start. Fix NEO4J_PASSWORD in .env, then reset Neo4j. Its data is only a copy of the graph, which the app reloads: 

docker compose rm -sf neo4j
docker volume rm solvay-spark-spine_neo4j-data
docker compose up -d neo4j
docker compose up -d app

If it was just slow (the first start downloads a plugin), wait for docker compose ps to show healthy and run docker compose up -d app again.

"pull access denied" or "unauthorized" when pulling the image.

The server isn't logged in to the registry. Run docker login reg.ivolve.cloud on the server.

The app keeps restarting.

Read docker compose logs --tail 100 app. A message about DATABASE_URL or a password means .env is incomplete; "connection refused" to postgres means the database isn't healthy yet.

The Evidence Agent says memory is unavailable.

Check the memory server and its log:

docker compose ps hindsight hindsight-db
docker compose logs --tail 50 hindsight
docker compose exec app curl -s http://hindsight:8888/health

hindsight-db must have exited with code 0. If it failed, Postgres wasn't ready or the password is wrong: run docker compose up -d hindsight-db hindsight again. If hindsight is still starting, wait 1–2 minutes. An AuthenticationError in its log means ANTHROPIC_API_KEY in .env is missing or wrong; fix it, then docker compose up -d hindsight.

Data looks wrong

The knowledge graph counts differ from my Mac.

A file is missing on the server. The graph is built from solvay-spark/*/markdown, knowledge_base/ and the database. The first deployment showed 370 BPML processes instead of 1976 because knowledge_base/ hadn't been copied. Re-run the two rsync commands (section 6), then rebuild the graph (section 11).

Ask returns nothing, or an error about embeddings.

Check the model downloaded and the index was restored:

docker compose logs ollama-pull | tail -3
docker compose exec postgres psql -U spark -d solvay -c "select count(*) from rag_chunks;"

The first should end in success; the second should print a number well above 0. If it's 0, restore the dump again (section 8).

Documents added in the UI don't save.

The container runs as user id 1000 and must be able to write knowledge_base/. On the server: sudo chown -R 1000:1000 ~/solvay-spark-spine/knowledge_base.

I changed POSTGRES_PASSWORD and now nothing connects.

Postgres kept the old password. Put the old one back, or reset the database, which deletes it, and restore the dump again: 

docker compose down
docker volume rm solvay-spark-spine_pgdata
docker compose up -d postgres
Before sharing it widely

Security, and what isn't included

The API has no login

The app's sign-in page protects the pages only. Every /api/* endpoint answers anyone who can reach the port. That's why the app listens on 127.0.0.1:8030 and is reached through a tunnel. Don't change APP_PORT to plain 8030 and open the port to the internet: the SPARK corpus would be readable by anyone.

Giving the team a web address

For a proper URL such as https://spark.ivolve.cloud, keep the app on localhost and put a reverse proxy in front of it:

  1. A DNS record pointing the name at 13.204.129.141, from whoever manages the domain.
  2. Ports 80 and 443 open in the EC2 security group, ideally to the team's IP addresses only.
  3. A reverse proxy (e.g. Caddy) that serves HTTPS and forwards to 127.0.0.1:8030. Check first whether the server already has one, since other apps run there: sudo ss -ltnp | grep -E ':(80|443) '.
  4. A password at the proxy (Caddy's basic_auth), so the API is covered too.

Other rules

  1. Keep secrets out of git: the .pem key, .env and database dumps. .gitignore and .dockerignore already exclude .env and backup/.
  2. Share credentials one to one, not in team channels.
  3. Data leaves the server when someone asks a question: the question and the retrieved excerpts go to Anthropic. Hindsight also sends each investigation's findings to Anthropic, to file them as memories.

Not included on the server

The local MLX vision model. It runs on Apple chips only. The Claude and OpenAI vision options and Tesseract still work.

Memories start empty on the server

The server's Hindsight has its own memory bank. Memories built up on a Mac aren't copied over; the server's bank fills as people run investigations there.

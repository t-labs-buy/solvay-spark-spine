AGENT MEMORY

Hindsight in Spark AI Spine

How the Evidence Agent remembers what it worked out last time — what gets written down, what comes back, and the one rule that keeps a memory from ever becoming a citation. Written for someone who has never used Hindsight, and for the architect who has to decide whether it belongs here.

Audience — engineers & architects, no prior Hindsight knowledge assumed Client — backend/agents/fitgap/memory.py Server — ./scripts/hindsight.sh on 127.0.0.1:8888 Status — all three operations live
Contents
Part 1 · Orientation

The problem it solves

Who — everyone Needs first — nothing

The Evidence Agent answers questions about the Solvay SPARK corpus. Ask it about the SOVOS interface and it searches, reads chunks, walks the knowledge graph, and writes an answer where every claim carries the passages that support it.

Then it forgets all of it. The next question about the same interface starts from nothing and re-derives the same conclusions, spending the same tool budget to get there. The corpus has not changed. Only the agent's ignorance has been restored.

What an agent memory actually is

Not a cache and not a second database. It is a store of conclusions — what earlier runs established, in the words a later run would need to hear. A cache would return the same answer to the same question. A memory tells the next run where to look, and then gets out of the way while that run proves it again from the corpus.

Hindsight (MIT, by Vectorize) is the service that does this. It stores facts, consolidates them into observations, and searches with four strategies at once — semantic, BM25, an entity graph and a temporal arm. It runs as a separate HTTP server; this repository ships only the client half and a policy about what may be written.

The client backend/agents/fitgap/memory.py — transport, timeouts and the rules about what a run may read and write.
The judgement backend/agents/evidence/agent.py — what an investigation is worth remembering. That is a decision about evidence, so it lives with the agent.
The server ./scripts/hindsight.sh — a separate process with its own virtualenv, its own models and its own Postgres.
Part 2 · The model

RETAIN, RECALL and REFLECT

Who — everyone

Hindsight has exactly three operations. Two of them belong to the agent and happen on every investigation. The third belongs to you and happens when you press a button.

Before the first search
RECALL Searches the bank and puts what it finds in front of the agent, as a preface to the question.
orients
The investigation
Evidence Agent
  1. Searches the corpus and walks the graph.
  2. Verifies every quote against what a tool returned.
  3. Submits claims, each carrying its sources.
concludes
After the answer
RETAIN Writes down what survived verification. Hindsight splits the note into typed facts.

REFLECT sits outside that loop entirely. It reads the whole bank and writes an answer from it — a briefing, not a search result — and only a person can trigger it.

Operation What it does Who triggers it Where it lives
RETAIN Writes what a run established. Hindsight's own model splits the note into typed facts. Every investigation, after finalise() memory.py:228 ← agent.py:671
RECALL Searches those facts and prefaces the question with the best of them. Every investigation, before the first tool call memory.py:199 ← agent.py:496
REFLECT Reads the bank and writes a briefing from it. A person, via Ask memory memory.py:285 ← app.py:2543

The four kinds of fact

You never choose these. RETAIN hands Hindsight a paragraph of prose and its extractor decides what kind of fact each sentence is. The bank today holds 35 facts across 3 investigations:

TypeMeansIn the bank now
worldA durable fact about the programme.20
observationSomething noticed in a run, consolidated across several.15
experienceSomething that happened to the agent itself.0
opinionA judgement, held rather than proven.0
Why the counts are lopsided

The agent retains conclusions about documents, so almost everything it writes is a world fact or becomes an observation once consolidation merges it with earlier ones. experience and opinion are real Hindsight categories that this integration simply does not produce much of — and that is the healthy shape. An opinion in an evidence bank would be a claim nobody has to prove.

Part 3 · The rule

Memory orients. It never grounds.

Who — architects, reviewers Weight — the load-bearing idea

This is the whole design, and everything else follows from it. If you read one section, read this one.

A claim in this system is carried by a quote, and every quote is verified character-for-character against session.retrieved — a set that only the retrieval tools write to. Nothing recalled from memory is in there. So a quote taken from a memory fails verification, and the claim it was supporting falls to the floor.

What that buys you

A remembered fact is structurally incapable of becoming a citation. Not discouraged by a prompt — incapable. The machinery that drops unverifiable quotes already existed for hallucinated ones; memory simply inherits it.

So memory is allowed to do one thing: decide where to look first. Which document to open, which route turned out to be an artefact last time. Then the run proves it again, from the corpus, or it does not get to say it.

Two rules that follow

1Only verified claims are ever written down

worth_remembering() keeps only claims that still carry a source. By the time it runs, finalise() has already dropped every quote that was not found in the chunk it named — so a claim with no sources left is one whose evidence did not hold up.

Why this one is not optional

Nothing downstream re-checks a memory. A claim that failed verification, written into the bank, would be believed forever — and would arrive in future runs looking exactly like a finding. Memory is the one place in this system where a mistake does not get a second review.

2A holdout run neither reads nor writes

Holdout hides the fit registers to measure the agent against a corpus it cannot cheat on. A previous run's answer arriving through memory would quietly answer the question being asked, and the measurement would be of the memory rather than the agent. Writing is refused for the mirror of that reason: a holdout answer was reached without half the corpus and is not a finding about it. 

def allowed(enabled: bool, holdout: bool) -> bool:
    """Whether this run may read and write memory. The rule, in one place."""
    return bool(enabled) and not holdout
Why that is a named function

It has exactly one call site and could have been written inline. It is named because it is the kind of condition somebody simplifies while tidying up, and nothing downstream would notice — the run would still answer, the panel would still render, and an evaluation would quietly start scoring the memory.

Part 4 · Architecture

Where memory sits beside RAG and the knowledge graph

Who — architects

The agent has three sources of information and they are not interchangeable. Confusing them is the most common mistake people make when they first see this.

Source Answers Citable? Reached by
RAG “What does the corpus say about X?” — passages, hybrid vector + BM25 over pgvector. Yes — this is the ground truth search_corpus, get_chunk
Knowledge graph “What is connected to what?” — identity, routes, counting. Yes — as graph facts, separately scored graph_entity, graph_neighbors, graph_path, graph_enumerate
Memory “What did we work out last time?” — conclusions from earlier runs. No — by construction Not a tool. A preface. See below.

Why memory is not a tool

Every other source is a tool the agent may call. Memory is text prepended to the first user message, before the question. That is a deliberate asymmetry, for two reasons:

  1. The budget — an investigation gets 14 tool calls. Every one spent on memory is one not spent on evidence, and memory cannot be cited, so it can never repay that call the way a retrieval can.
  2. The timing — a note is only useful before the first search. By the time the agent would think to call a memory tool, it has already chosen where to look.

The preface says what it is, in the agent's own context:

═══ WHAT EARLIER INVESTIGATIONS FOUND ═══

These are notes from your own past runs over this corpus. They are NOT
EVIDENCE. Nothing below is retrievable, and nothing below may be quoted or
cited: a quote that is not in a chunk a tool returned to you in THIS run is
discarded automatically and its claim falls to the floor.

Use them for one thing only -- deciding where to look first. Then prove it from
the corpus. If what you retrieve contradicts a note, the corpus wins; say so in
your answer, and do not repeat the note.
Belt and braces, on purpose

The preface is not what makes memory safe — the quote verification is. The preface exists so that a model reading its own context understands why a note it cannot cite is in front of it, and so that it reports a contradiction instead of silently preferring one source. Remove the preface and the system is still sound; remove the verification and it is not.

The two embedding models are different, and that is fine

IndexModelRuns on
Corpus (RAG)bge-m3, 1024-dYour local Ollama
Memory bankBAAI/bge-small-en-v1.5In the Hindsight process

They never compare vectors with each other, so they do not need to agree. The memory bank is searched only against memory; the corpus only against the corpus.

Part 5 · Walkthrough

One investigation, step by step

Who — engineers Needs first — the memory server running

Turn on the memory toggle beside holdout on the Evidence Agent, ask a question, and this is what happens.

1The rule is checked

allowed(enabled, holdout). If holdout is on, memory is off regardless of the toggle, and the run records that it was suppressed rather than pretending it was never asked for.

2RECALL searches the bank
remembered = agent_memory.recall(question)   # up to 6 memories, 1200 tokens
if remembered:
    prompt = f"{memory_note(remembered)}\n\n═══ THE QUESTION ═══\n\n{prompt}"

Four search strategies run at once inside Hindsight and the results are merged. Nothing here is a vector lookup you have to tune.

3The log records the prompt as assembled
Why that matters for debugging

Between the question you typed and what the model read sit a scope note and, with memory on, a page of notes from earlier runs. A reader who only sees the question cannot tell why the agent went where it went. The Logs drawer carries the real thing.

4The investigation runs normally

Up to 14 tool calls across RAG and the graph. Memory changes nothing about how a claim is built or scored — it only changed where the agent looked first.

5RETAIN writes down what survived
final = finalise(submitted, session, engines, calls, ...)   # drops bad quotes
if use_memory:
    written = worth_remembering(final)     # verified claims only
    agent_memory.retain(written, context=..., metadata=..., tags=[...])

The call is asynchronous on the server: it returns as soon as the text is accepted, because fact extraction is an LLM job and an investigation that has already answered must not wait on it.

What you have now

An answer on screen, and a note in the bank that the next run about this area will be handed before its first search. The Memory panel shows exactly what was recalled, and the Logs drawer shows exactly what was written back.

An answer that found nothing is still worth keeping

“We looked for this and the corpus does not address it” is one of the most valuable notes in the bank. It is exactly what stops the next run spending its whole budget re-discovering the same absence.

Part 6 · REFLECT

Asking the memory instead of the corpus

Who — analysts, leads Costs — a model call per press

RECALL retrieves. REFLECT answers: it runs an agentic loop of searches over the bank and writes a briefing. The Ask memory button on the Evidence Agent is the only way to reach it.

It answers what nothing else can

No corpus document says which interfaces have been investigated, or where two runs disagreed with each other. That only exists across the bank. Asked the second question, a real reflection over this corpus found:

SourceBilling block named
Returns workshop deck (L2C-WS020, 16.07.2025)Block 80, “Check credit memo”
Training topics deckA new block Z4, for return billing type CBRE

Two documents naming different codes for the same control point. No single run had reported that as a conflict, because no single run had seen both halves.

Why it is a panel and not a tool

A summary of summaries

A memory is already a model's reading of a run. A reflection is a model's reading of those. The structural guarantee still holds — nothing reflected is in session.retrieved, so none of it can be cited — but prose the agent cannot check belongs in front of a person who can. A test fails if backend/agents/evidence/agent.py ever so much as mentions reflect.

What the panel shows

  1. The briefing — rendered markdown, framed as “not evidence” before the first line of it.
  2. How it looked — the searches the reflection actually ran. A reflection that searched the wrong words explains an answer that missed something, and nothing else would say so.
  3. What it read — every memory those searches returned, with its fact type.
  4. What it cost — tokens in and out. This is the one button in the application that spends real money per press.
Where the provenance comes from, and why not based_on

ReflectResponse.based_on is the obvious field and is documented as “evidence used to generate the response”. It is always empty here. Hindsight's own docstring says why: “based_on: Empty dict (agent retrieves facts dynamically)” — agentic reflect fetches facts through tool calls rather than being handed a set.

Reading it produced an answer with no sources and no error, which looks exactly like a server that forgot to send them. The panel asks for include_tool_calls instead and rebuilds provenance from the trace. The four tools (lookup, recall, learn, expand) do not agree on an output shape, so _facts_in() handles all of them and skips anything without text rather than guessing.

Questions worth asking a memory

The useful ones are all cross-run questions — the kind no single investigation and no document can answer:

  1. Which interfaces or specifications have we investigated, and what did each conclude?
  2. Where do two of our investigations disagree with each other?
  3. What questions were left open across all our investigations, and who owns them?
  4. What has the corpus turned out not to cover?

Asking it “what is the SOVOS interface?” is a waste of a model call. That is a corpus question — put it to the Evidence Agent, where the answer will come back with citations.

Part 7 · Setup

Running it yourself

Who — engineers Needs first — ANTHROPIC_API_KEY in .env

Start the server. It is a separate process from the app:

./scripts/hindsight.sh

It prints what it is using:

Hindsight: litellm / anthropic/claude-opus-5 on 127.0.0.1:8888
           reflect on anthropic/claude-sonnet-5 (60s per call)

With the server up, the memory toggle on the Evidence Agent becomes available and Ask memory lights up. With it down, both grey out and investigations run exactly as they did before — every call is best-effort.

Client configuration

VariableDefaultNotes
HINDSIGHT_URLhttp://127.0.0.1:8888Empty switches memory off entirely.
HINDSIGHT_BANKspark-evidenceA second bank is how you keep two corpora apart.
HINDSIGHT_TIMEOUT8Seconds. Far below the client's own 300s default, which would let a sick server stall an investigation.
HINDSIGHT_RECALL_TOKENS1200The ceiling on what one recall may put into the agent's context.
HINDSIGHT_REFLECT_TIMEOUT120Seconds, for reflect only — it gets its own client.

Which model, and why it is two of them

Retain runs on Opus; reflect runs on Sonnet. That split is a deadline decision, not a cost one. 

LiteLLM tool call exceeded timeout=30.0s (scope=reflect_tool_call), retrying...
LiteLLM tool call timed out after 30.0s on 4 attempts
[REFLECT] LLM error on iteration 3: TimeoutError (127023ms)

Reflect is the one interactive operation — a person is holding an HTTP request open — so Hindsight gives each call inside it 30 seconds, chosen against calls “answering in 1-4s” times a retry ladder of three. Opus does not answer in 1-4s. Raising the deadline makes a working reflection take minutes, because the ladder multiplies it.

Why Opus keeps retain

Extraction decides what the bank believes forever, and it runs in the background against a queue where a slow call costs nothing. Reflect is reading and summarising, which Sonnet does well and quickly — 35 to 50 seconds end to end.

Why Claude goes through LiteLLM and not Hindsight's own provider

Two dead ends, both worth knowing so nobody re-walks them:

  1. The anthropic provider builds an httpx.Timeout and hands it to a client that has migrated to httpx2, which rejects it outright. The whole anthropic 1.x line is on httpx2, so there is no version to pin back to.
  2. The openai provider against api.anthropic.com/v1/ — chat works, but fact extraction asks for response_format {"type": "json_object"} and that endpoint answers 400: “Input should be 'json_schema'”.

LiteLLM speaks Anthropic's native API and translates the request Hindsight actually sends.

Always set the model explicitly

There is no default worth relying on. Hindsight's own defaults are claude-haiku-4-5 for the anthropic provider and gemma3:12b for ollama — and a model that is not there fails every write silently, because retain is asynchronous. The API accepts it, the agent moves on, and nothing is ever learned.

Part 8 · Evaluation

Measuring whether it actually helps

Who — architects, anyone defending the spend

“The agent gets smarter over time” is a claim, and this system is built to make claims checkable. Here is how to check this one.

Every run records what memory did

evidence_runs carries a memory JSON column beside the run's tool calls, timings and answer — so a memory-on run and a memory-off run of the same question are directly comparable. 

SELECT question,
       COALESCE((memory->>'used')::boolean, false)        AS mem,
       jsonb_array_length(COALESCE(calls,'[]'::jsonb))    AS calls,
       seconds,
       COALESCE(jsonb_array_length(answer->'claims'), 0)  AS claims,
       answer->>'state'                                   AS state
FROM   evidence_runs
WHERE  status = 'done'
ORDER  BY question, mem;

Run against this database today, for one question:

question: "Explain customer return management process"

memory  calls  secs    claims  state
False   14     120.2   9       supported
False   14     185.5   14      supported
True    11     187.8   9       supported
Read that honestly

Two runs without memory, one with. The memory-on run used 11 of its 14 tool calls where both memory-off runs hit the ceiling — which is the effect you would hope for, and is nowhere near enough data to conclude anything. Two memory-off runs of the same question disagree with each other by 5 claims. That is the size of the noise you are trying to measure through.

What a real measurement would need

  1. The evaluation set — 27 questions ship with the app, across PKG, DR and both. Run all of them each way.
  2. A fixed prompt_hash — every run records the SHA-256 of the system prompt. Change the prompt and runs either side of it are not comparable; the hash is what tells you.
  3. A fixed corpus_fingerprint — same argument for the documents underneath.
  4. Order that does not favour memory — run all memory-off first and memory-on second and you have measured the bank filling up, not the feature.

What to measure, in priority order

MetricWhy it is the right one
Tool calls usedThe clearest signal. Memory should let a run reach the same answer in fewer steps, and the 14-call ceiling makes “ran out of budget” visible.
Answer stateA run that reached supported without memory and not_in_corpus with it is a regression, loudly.
Claims with sourcesMore claims is not better. Same claims from fewer calls is.
SecondsUseful, but noisy — it moves with model latency, not just with effort.
The check that cannot be gamed

Run the evaluation set under holdout. Memory is refused in both directions there, so a holdout score is a measurement of the agent against a corpus it cannot have memorised. If holdout scores move when you turn memory on, something is wrong with the wiring, not with the agent.

Part 9 · Practice

Getting value out of it

Who — everyone
1Ask related questions in a batch

Memory pays off when a later run covers ground an earlier one already walked. Five questions about the returns process in one afternoon will compound; five questions about five unrelated areas will not.

2Leave memory off for the first run in a new area

There is nothing to recall, and the run still writes. You pay nothing for the toggle being off and the bank fills either way.

3Read the Memory panel when an answer surprises you

It shows exactly what the agent was told before it started. An answer that went somewhere odd usually has a note in that panel explaining why.

4Treat the bank as something that needs weeding
There is no per-fact delete

Hindsight exposes DELETE on a document (one retain and everything derived from it) and on the whole bank — not on an individual fact. So a bad memory is removed by deleting the run that produced it. Check first that the document produced only facts you want gone: deleting one that mixes a bad fact with good ones loses both.

5Never let tests write to the real bank

This one is from experience. retain was stubbed per-test, and one test about log ordering drove a run with memory=True without stubbing it. Every run of the suite put two more facts about a fabricated interface into the bank the application reads. They consolidated, came back in recalls, and were indistinguishable from findings — because by then that is exactly what they were.

How it is prevented now

The stub is global and set at import, so a test cannot write by accident, and a test checks that the guard is in place. recall is deliberately left real: it only reads, and letting it talk to a live server is the one thing that exercises the transport.

6Keep an eye on what reflect costs

A reflection reads the whole bank, so the input side grows as the bank does. Over 35 memories a reflection ran 36,000–71,000 input tokens. The panel prints the figure under every answer for exactly this reason.

Part 10 · FAQ

Questions people ask

Who — new users & architects

If memory cannot be cited, what is it actually worth?

Direction. An investigation's expensive decision is where to look first, and it makes that decision with 14 tool calls to spend. A note that says “the billing block question is in the L2C-WS020 deck, and the training deck disagrees with it” does not prove anything — it saves the three calls it would have taken to find the deck.

Does the agent's prompt get rewritten as it learns?

No. The system prompt is fixed and its SHA-256 is recorded with every run. What changes is the context the model is handed: recalled notes are prepended to the first user message. Nothing fine-tunes, and nothing edits the prompt. That is what makes two runs comparable at all.

Is this RAG over a second corpus?

No, and the difference is the point. RAG retrieves passages that can be quoted. Memory retrieves conclusions that cannot. They use different indexes, different embedding models, and are reached by different mechanisms — a tool call versus a preface.

What happens if the memory server is down?

Investigations run and answer exactly as before. Every call is best-effort and short-deadline: recall returns empty, retain returns false, and the page greys out the toggle with the reason rather than offering something that will fail on the press.

Could a wrong memory poison future answers?

It can waste a run's time by pointing it somewhere unhelpful. It cannot put an unsupported statement into an answer, because the statement would need a quote and the quote would need to be in session.retrieved. The realistic failure is a slower or less complete investigation, not a false claim.

Does memory leak between the holdout and normal runs?

No, and it is enforced in one named function rather than inline. A holdout run neither reads nor writes, in both directions.

Where does the data physically go?

Into the Hindsight server's own Postgres on this machine. The text of an investigation note is sent to whichever model the server is configured with, because fact extraction is an LLM job — so the provider choice in hindsight.sh is also a data-residency choice. The ollama provider keeps it on the machine entirely.

Only the Evidence Agent uses it. Why not the Fit-Gap Copilot?

Nothing prevents it — the transport lives in backend/agents/fitgap/memory.py precisely so it can. What is missing is the judgement half: an equivalent of worth_remembering() that decides which parts of a fit-gap analysis are safe to keep. That is a decision about evidence, not a wiring task.

What is the next capability worth adding?

Mental models. A mental model is a standing reflect — precomputed against a source query, refreshed on a trigger, readable at zero latency. That is the only shape that would let a dense synthesis sit in front of an investigation without putting an LLM call on the hot path, which is the one thing reflect cannot do. The bank holds none today.

How do I see what is in the bank right now?

Hindsight ships its own UI on the same port, and the bank is also readable over HTTP: 

curl -s "http://127.0.0.1:8888/v1/default/banks/spark-evidence/memories/list?limit=100" \
  | python3 -m json.tool | head -40

Re-run the query in that section before quoting the numbers; the bank grows.

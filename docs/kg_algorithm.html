Ontology 101 · Building Blocks

Core Concepts Explained in Everyday Language

Prerequisites — None (plain English)

Before looking at code or algorithms, let's establish four intuitive metaphors that explain how knowledge graphs work:

1. Entities (The Nouns / Nodes)

Think of an Entity as a real-world object, concept, or document. In our graph, an entity is a colored circle (node). Examples: SAP S/4HANA, Lead-to-Cash (L2C), SPARK-10825, or O-030-010.

2. Relationships (The Verbs / Edges)

A Relationship is the directed line connecting two nodes. It explains how they relate. Examples: [Salesforce] ⬅ (mentions_system) ⬅ [Doc 14] ➔ (mentions_system) ➔ [SAP S/4HANA].

3. Ontology (The Master Blueprint)

An Ontology is simply the rules of grammar for the graph. It defines what categories can exist and how they are permitted to connect. It dictates that a "Functional Spec" belongs to a "Document", and a "Document" belongs to a "Business Stream".

4. Topology (The Physical Shape)

Topology describes the physical layout and clustering of the network. High-traffic "hub" nodes (like SAP S/4HANA with 68 connections) naturally anchor the center, while specialized ticket specs orbit around them like moons around a planet.

Deep Dive into the 4 Extraction Rules

Rule A: Stream Association

The engine scans the document title and the first 600 characters of prose. If it spots stream indicators (e.g., L2C, I2D, R2R, P2P), it immediately binds the document node to the respective Macro Stream hub via a belongs_to edge.

Rule B: Enterprise System Fingerprinting

The engine examines document text for system signatures: Any of the 18 systems' word-bounded patterns ➔ one mentions_system edge.
What kind of system it is (sap, legacy_erp, middleware, …) is the System node's kind property, not the edge's type.
Each edge records its evidence: method, mentions, chunk_count and the chunks that name the system.

Rule C: BPML Process Code Hierarchy

Using regex pattern \b([A-Za-z][A-Za-z0-9]{0,3})-(\d{2,3}(?:-\d{2,3})+)\b, the engine extracts codes like O-030-010. It then splits the code numbers to identify the parent process (O-030) and generates a subprocess_of relationship automatically!

Rule D: JIRA Ticket Disambiguation

Using regex pattern \bSPARK[-_ ]?(\d{4,6})\b, it discovers all ticket references. If the ticket number is in the document filename, it flags the document as the Primary Implementing Spec (implements_ticket); otherwise, it links it as an incidental reference (references_ticket).

View the Core Python Extraction Logic

This snippet from knowledge_graph.py shows how processes and tickets are mined:

# Extract BPML Process Codes
found_codes = set(CODE_RE.findall(content))
for prefix, code_num in found_codes:
    full_code = f"{prefix}-{code_num}"
    proc_id = f"proc:{full_code}"

    add_node(proc_id, full_code, "process", description=f"BPML Process Step {full_code}")
    add_edge(doc_id, proc_id, "specifies_process", "Specifies Process")

    # Automated Hierarchy: Link sub-process to parent process
    parts = code_num.split("-")
    if len(parts) > 1:
        parent_code = f"{prefix}-" + "-".join(parts[:-1])
        parent_id = f"proc:{parent_code}"
        add_node(parent_id, parent_code, "process", description=f"Parent Process {parent_code}")
        add_edge(proc_id, parent_id, "subprocess_of", "Subprocess of")

AI Architecture · Retrieval Mechanisms

Why Vector RAG Fails Where Knowledge Graphs Excel

Technology Comparison — Vector Embeddings vs Topological Graphs

Traditional AI search engines use Vector RAG (Retrieval-Augmented Generation). They take your 83 files, chop them into small 500-word text chunks, calculate a mathematical embedding vector (like an OpenAI 1536-dimensional coordinate), and store them in a vector database like Pinecone or ChromaDB.

While Vector RAG is great for generic semantic search (e.g., "What is Solvay's policy on travel expenses?"), it suffers from catastrophic failures when applied to complex enterprise systems:

Traditional Vector RAG (Semantic Similarity)

• Chunk Fragmentation: If Document A says "Salesforce connects to Doc 12" and Document 12 says "Doc 12 sends tax records to SOVOS", the vector database has chopped them into separate chunks. It cannot bridge the connection between Salesforce and SOVOS.
• Blind to Multi-Hop Logic: Vector cosine distance measures how similar words sound, not how systems integrate.
• Hallucination Risk: Returns chunks that use similar buzzwords, even if they have no functional relationship.

Our Knowledge Graph (Topological Lineage)

• Deterministic Multi-Hop Discovery: Traverses the actual network paths. It mathematically proves: [Salesforce] ➔ [Doc 12] ➔ [SOVOS] in 2 hops.
• Zero Hallucination: Every single node and relationship is verified against the source text.
• Global Structural Awareness: Understands that O-030-010 is a sub-step of O-030 without needing that sentence repeated in every chunk.

The Best of Both Worlds

In Solvay Spark Spine AI, we unite the graph with AI: the knowledge graph discovers the exact mathematical sub-network of entities, and then feeds this high-precision context to the AI model. The AI synthesizes a clear, human explanation that is 100% grounded in the real architecture.

Graphics Engineering · 60 FPS Performance

Under the Hood: D3 Force Physics & Canvas Rendering

Technology — HTML5 Canvas API + d3-force Frame Rate — Consistent 60 FPS (720+ nodes)

Rendering an enterprise graph with over 720 nodes and 1,200 relationships poses a massive web performance challenge. Most introductory graph tutorials use SVG (Scalable Vector Graphics). However, in an SVG graph, every single node, circle, text label, and edge requires a distinct DOM (Document Object Model) element. With over 2,500 DOM elements recalculating positions on every physics tick, browsers stutter, animations lag, and mobile devices overheat.

HTML5 Immediate-Mode <canvas> (Our Approach)

• Single DOM Node: Exactly one <canvas> element in the DOM tree.
• Direct GPU Acceleration: The browser's 2D rendering pipeline paints thousands of shapes and labels directly onto the pixel buffer.
• Rock-Solid 60 FPS: Panning, zooming, and physics animations remain buttery smooth regardless of network size.

Traditional SVG Graphs (Rejected)

• 2,500+ DOM Nodes: Every circle and line is a separate DOM node.
• Heavy Reflow Penalties: Moving one node triggers expensive browser layout recalculations and style recomputations.
• Laggy Dragging: High CPU consumption, dropped frames, and memory bloat on standard enterprise laptops.

Mathematical Mouse Hit-Testing on a Flat Canvas

Because an HTML5 Canvas is a single flat raster image, there are no individual DOM elements to listen for mouse clicks or hover events. To make every node clickable and responsive, our frontend implements mathematical spatial coordinate hit-testing: 

// In KnowledgeGraphPage.tsx: Transforming screen mouse coords into graph simulation coordinates
const canvas = canvasRef.current;
const rect = canvas.getBoundingClientRect();
const screenX = event.clientX - rect.left;
const screenY = event.clientY - rect.top;

// Invert the active pan & zoom transformation
const transform = transformRef.current;
const simX = (screenX - transform.x) / transform.k;
const simY = (screenY - transform.y) / transform.k;

// Check Euclidean distance to every node
for (const node of nodes) {
  const dx = simX - node.x;
  const dy = simY - node.y;
  const radius = node.size + 4; // Hit-box padding
  if (dx * dx + dy * dy <= radius * radius) {
    return node; // Mouse is hovering over this entity!
  }
}

The 4 Physics Forces Shaping the Graph

1. Multi-Body Repulsion (Coulomb's Law)

Every node pushes away from every other node like magnets of the same pole. Major streams repel with a massive -1800 force, core systems with -750, and leaf tickets with -220, guaranteeing that large clusters never crush each other.

2. Link Spring Distances (Hooke's Law)

Edges act like flexible springs. Business stream links stretch to 240px to form wide planetary orbits; system links settle at 160px; and functional specifications orbit closely at 95px.

3. Radial Collision Buffers

To eliminate overlapping text labels, a rigid collision boundary is enforced around each node: node.size + 35px for streams, node.size + 24px for systems, and node.size + 16px for leaves.

4. Gentle Center Gravity

Instead of pulling all nodes into a tight ball, center gravity is tuned down to a delicate 0.015. This keeps the graph roughly centered while allowing natural breathing room across the entire canvas.

Troubleshooting & Clarifications

Frequently Asked Questions (FAQ)

Is an SQL query running behind the scenes when I search the graph?

No. There is no SQL database or relational tables involved. When you search, our engine executes fast in-memory graph algorithms in Python (Breadth-First Search for shortest paths, inverted set intersections for entity matching, and topological degree ranking). The results are rendered directly by your browser's GPU using D3.js canvas simulation.

Why do nodes not disappear when I hover over them anymore?

In earlier iterations, hovering over a node dimmed non-connected nodes to 8% opacity, which felt disorienting as the user moved the mouse. We upgraded the rendering engine: now, all nodes remain at 100% full color and brightness at all times. Hovering lights up the connected edges and arrowheads in brilliant cyan glow without causing the rest of the graph to vanish. If you truly want to hide unrelated nodes, you can click any node and press the "Isolate" button in the zoom dock.

Can I view the graph in Full Screen?

Yes! We built a dedicated "Full Screen" button in both the top navigation bar and the floating zoom dock. Clicking it immediately expands the graph over the entire browser window (bypassing the application tabs), and pressing Esc smoothly returns you to the normal view.

Can I minimize the "Graph Legend & Hints" box in the corner?

Yes. Simply click on the "Legend & Hints" header bar or its arrow button. It collapses into a tiny, unobtrusive pill badge in the bottom-left corner, giving you unobstructed visibility over that quadrant of the canvas.

What happens if a document has typos or formatting inconsistencies?

Our regex extractors use boundary assertions (\b) and case-insensitive flags. Even if an author writes spark-10825, SPARK 10825, or SPARK_10825, the normalization pipeline cleanses and maps all variations to the canonical SPARK-10825 entity ID.

Can we trust the knowledge graph? How it is checked, in plain words

The Solvay SPARK knowledge graph links thousands of programme documents to the systems, business processes and tickets they talk about. People query it by hand, and AI agents query it on their own. This tutorial explains how we check that the graph is correct, complete and up to date, and why its answers come from real documents rather than random text or random connections.

Audience — anyone relying on the graph, no technical background needed Where to see it — Knowledge Graph page → Quality view Code — backend/graph/graph_eval.py

In short

Did we evaluate the knowledge graph? The two-minute answer

A short, conversational summary for when a client asks whether the knowledge graph has been evaluated, using the figures from the checks run on 28 September 2026. The rest of this tutorial explains each point in detail.

Short answer

“Yes. We check the knowledge graph in two ways: the graph itself, and how well it answers questions. Both run from a Quality screen built into the tool, so the numbers aren’t a one-off exercise. We can rerun them whenever the documents change.”

How the graph is built (the point that builds trust)

“First, it helps to know the graph isn’t written by an AI. It’s built by fixed rules that find known system names, process codes and ticket numbers in your documents. So it can’t invent a fact. Every link comes from text that’s actually in a document. What can go wrong is a wrong match, a missed match, or the graph falling out of date, so those are what we measure.”

Check one: the graph itself

“We check it the way the research literature on knowledge graphs recommends: accuracy, completeness, consistency and freshness.”

  1. Accuracy — “every link points to the passages it came from. We checked all 4,537 of them against the real text, and every one holds up.”
  2. Completeness — “all 217 documents in the search index are in the graph, and every parent–child link from your official BPML process workbook is present, 1,846 of 1,846.”
  3. Consistency — “no broken links, no duplicates, no loops in the process hierarchy.”
  4. Freshness — “it confirms the graph was built from the current version of the documents.”

Check two: asking it questions

“People can ask the graph questions in plain English, and an AI turns them into a database query. We test that translation with 28 questions whose correct answers we worked out by hand. It gave the right answer to 24 of the 25 questions the graph can answer, and it correctly recognises questions the graph can’t answer, like ‘who approved this process’.”

Being candid (clients respect this)

“The checks also found things to fix, which is the point of running them. Four tickets have an inconsistent flag in the graph, and one type of question, ‘list everything’, can come back cut off at 100 rows. Both are known and tracked. The answer key for the question test is also still being reviewed by programme experts.”

If they ask “how do I know an AI agent isn’t just making things up?”

“Two safeguards. The agents can’t treat the graph as proof on its own: any claim has to be backed by a quote from a real document, and every quote is checked word for word before an answer is shown. And when an agent traces a connection between two systems, the tool judges whether that route means anything or is just a coincidence of how things are filed, and flags it.”

Closing

“There’s a plain-language write-up of all this, including what each measure means, that I’m happy to share.”

Start here

The knowledge graph in one minute

Think of the knowledge graph as a very large, very well-organised index card system. Every thing the programme talks about gets a card: each document, each IT system (SAP S/4HANA, Salesforce, SOVOS…), each business process step (such as 4.10.2 Process Returns), each SPARK ticket, and each business stream (Lead to Cash and the others). Then the cards are linked: “this document mentions this system”, “this step sits under that step”, “this document is the specification for that ticket”.

2,390 things 218 documents, 18 systems, 1,985 process steps, 165 tickets and 4 business streams.
4,789 links Six kinds of link, such as mentions system and specifies process.
8,867 passages The paragraphs of each document, so any link can be traced back to the exact text that justifies it.

Two kinds of reader use it:

People, by hand Exploring the picture on the Knowledge Graph page, or asking a question in plain English on the Cypher view.
AI agents, on their own The Evidence Agent and the Fit-Gap Copilot look things up in the graph while they research an answer.
Why check it at all

An index that quietly points to the wrong page is worse than no index: people trust it and stop checking. The Quality view exists so that trust is earned by measurement, and so a problem shows up on a screen before it shows up in a client workshop.

Background

How the graph is built, and why that matters for trust

The single most important fact about this graph: it is not written by an AI. It is built by fixed rules that look for known names and codes in the documents, much like a search for exact words.

Input
Programme documents Specifications, workshop notes, spreadsheets, converted to text.

Fixed rules

This shapes what can and cannot go wrong:

RiskPossible here?Why
Invented factsNoA link only exists where a document actually contains the name or code. Nothing is guessed or summarised.
A wrong matchYes, rarelyA word that merely looks like a system name, e.g. a customer called “Eccles” for SAP ECC. The rules are written to avoid known cases, and tests guard them.
A missed matchYesA system that is not on the list of 18 is simply not recognised.
Out of dateYesIf documents change and the graph is not rebuilt.
What this means

Because the graph cannot invent anything, its checks focus on the three things that can go wrong: wrong matches, missed matches and staleness. The rest of this tutorial walks through each check in turn.

The tool

The Quality view at a glance

Open the Knowledge Graph page and choose Quality in the view switcher at the top. It holds two separate checks:

1 · The graph itself Is the graph correct, complete, consistent, well-connected and current? No AI is involved, it costs nothing and takes seconds. It runs when you open the view, and whenever you press Check now.
2 · Plain-English questions When someone asks the graph a question in English, do they get the right answer? It uses Claude once per question, so it runs only when you press Run question check.

Five questions about the graph itself

The first check groups its measurements under five questions, the ones used in the research literature on knowledge graph quality: Accuracy (is it right?), Completeness (is it all there?), Consistency (does it contradict itself?), Structure (does it hang together?) and Freshness (is it current?). The next five sections take them one at a time.

Check 1 · The graph itself

Accuracy: is every link backed by real text?

Cited passages name their target

Every link in the graph carries a small list of the passages it was found in, like a footnote. For example, the link “SOVOS interface specification mentions SAP CPI” cites the two paragraphs where CPI appears.

This check goes to every one of those footnotes, fetches the paragraph from the same store the search engine uses, and checks that the paragraph really names the thing the link points to.

Why check against the search store

The graph could agree with itself and still be wrong, for example if the documents were re-indexed and the paragraph numbers moved. Checking against the text that search actually serves catches exactly that.

Today

4,537 of 4,537 cited passages name their target: Pass. A further 23 links rest on a document’s file name alone, e.g. a file called “…SPARK-21175…”, and have no passage to check. They are reported separately rather than counted as passes.

A real finding

The four contradictions are genuine: tickets SPARK-18542, 21175, 21266 and 21930 each have a specification document named after them, but the graph does not flag them as having one. This had already been noticed for two of them, and the check found the other two. It is a small bookkeeping error in how the graph is built, not an error in the documents, and it is the kind of thing this check exists to surface.

Why hubs matter: the airport problem

Almost every flight in a region connects through one big airport, so “you can fly from A to B” tells you very little: everything connects to everything through the hub. The graph has hubs too. The BPML workbook, for instance, is linked to over 1,500 process steps. A route between two systems that passes through such a hub does not mean the systems exchange data.

That is why hubs are counted here, and why the AI agents are told about them (see How we know it is not making things up).

About the 14 unconnected things

Ten are documents in which no known system, stream, ticket or process code was found, such as a meeting-notes template, a few spreadsheets and some CRM exports. The other four are process steps that no document cites. Neither is an error, but a steady rise would be worth a look.

What you have now

You have seen every measurement of the graph itself. Together they answer “is the graph right, complete, consistent and current?”. The next section turns to the second question: are the answers right?

Check 2 · Asking questions

Plain-English questions: does a question get the right answer?

On the Cypher view, anyone can type a question such as “Which documents mention both SOVOS and SAP CPI?”. Claude translates it into a database query (in a language called Cypher), and the query is run against the graph. The risk is not the graph but the translation: Claude might misunderstand the question and ask the database for the wrong thing.

How the check works

1A set of reference questions with known answers

28 questions, each with a reference query written and tested by hand, stored in data/graph_eval_questions.json. Three of them are deliberately questions the graph cannot answer, such as “Who approved the returns process?”. Approvals are not in the graph.

2Claude answers each question as a user would see it

The same translation step the Cypher view uses, with no special help.

3Both queries are run and their results compared

What counts is the result, not the wording of the query: two differently written queries that return the same rows are both right. This is called execution accuracy, and it is the standard way such systems are scored.

What the first run found

One real miss: asked to list all 130 process codes that are not in BPML, Claude’s query stopped at the first 100. Any “list everything” question with more than 100 answers is at risk of coming back incomplete, so this is a known improvement for the translation step. The two “knew what it could answer” misses were questions about what a document says: Claude correctly explained that the graph does not hold document text, but still offered nearby passages instead of declining.

The reference answers are reviewed by people

A test is only as good as its answer key. The reference answers are marked not yet reviewed, and the Quality view shows a warning, until someone who knows the programme has checked them. When a reference is corrected, the last run can be re-scored without asking Claude again.

The key question

How we know it is not retrieving random text, following random paths or making things up

This is the question that matters most, so here is the whole chain, for people querying by hand and for AI agents. No single safeguard is enough on its own; they are layered so that each one catches what the one before might miss.

The worryThe safeguard
“The answer is made up.”The answer is rows read from the graph, not text written by an AI. Claude only writes the question for the database; the database supplies the answer.
“It misunderstood my question.”The query and a plain explanation of what it looks for are shown next to the answer, so a misunderstanding is visible. The question check measures how often this happens.
“It answered something it could not know.”Claude is required to say when the graph cannot answer, e.g. who approved something, and the question check tests exactly that.

“A query could change or damage the data.”Queries run in a read-only mode enforced by the database itself. A query that tries to write is refused. Results are capped, and slow queries are stopped after 20 seconds.

When an AI agent uses the graph

The agents are held to a stricter standard than a person, because nobody watches each step as it happens.

1The graph can point, but it cannot prove

An agent’s claim that rests only on the graph, with no quoted passage, is capped at a low confidence (0.35 out of 1). To be trusted, a claim needs a quotation from a real document. The graph earns a small bonus (+0.10) only when it confirms something a document already says.

2Every quotation is checked word for word

Before an answer is shown, every quote the agent uses is checked against the document it names. A quote that is not found word for word is thrown away, and the Evaluation tab counts how often that happens.

3Routes through the graph are judged, not trusted

When an agent asks “how is system A connected to system B?”, the route it finds is given a verdict:

The route…VerdictWhy
passes through a business streamNot a real connectionTwo systems in the same stream are like two people in the same department: that does not mean they talk to each other.
uses a classification link (belongs to, sits under)Not a real connectionThese record how things are filed, not how data flows.
passes through a hubPossibly real, with a warningThe airport problem: confirm it against an interface specification first.
uses only links found in document textRealEvery step is backed by passages that can be read.
4Every run is scored

Each agent run gets its own quality scores: quotes verified, claims without evidence, tools used correctly, guardrails respected. They appear on the agent’s Evaluation tab.

The short answer

The graph cannot invent facts, because it is built by rules from real text. Every link can be traced to its source passage, and all of them are checked. Answers are database rows, not generated prose. Agents cannot rely on the graph alone, their quotes are verified word for word, and misleading routes are flagged rather than trusted.

Honest limits

What the checks cannot tell you

Every measurement has an edge. These are the ones worth knowing:

  1. A correct match is not always a meaningful one — a document that names SAP CPI once in passing is linked exactly like the CPI interface specification. The link is true, but its importance varies. The count of mentions on each link helps; judging meaning needs a person reviewing a sample.
  2. Only known names are found — the graph recognises 18 systems. A system missing from that list is invisible to it, however often it is mentioned.
  3. The graph holds headings, not text — it can say which passages mention SOVOS, but not what they say. For that, use Ask RAG or the Evidence Agent, which read the text.
  4. Mentions are not truth — if two documents disagree, the graph records both mentions faithfully. Deciding which document is right is the Evidence Agent’s job, which reports a conflict when it finds one.
  5. The question check is a sample — 28 questions cannot cover every question a person might ask. It is a smoke test for the translation step, not a guarantee.
For client conversations

Questions a client is likely to ask

Can the knowledge graph hallucinate?

No. The graph is built by fixed rules from the documents, not generated by an AI, so every link corresponds to a name or code actually present in a document. The part that uses AI, translating an English question into a database query, is shown to you and measured by the question check.

How accurate is it, in numbers?

At the last check, all 4,537 passages cited by the graph’s links name what the link points to, and plain-English questions returned the correct answer 24 times out of 25. The Quality view always shows the current figures.

Can I trace an answer back to the original document?

Yes. Every link records the passages it came from, and every item in an answer can be opened on the graph and followed to its document and section.

What happens when documents are added or changed?

The graph is rebuilt from the documents, and the freshness check shows immediately if the graph, or its question copy, is older than the documents.

How do I know an answer is complete?

The completeness checks confirm every indexed document is in the graph and every process link from the official workbook is present. For a single answer, the Cypher view says when a result was stopped at the application’s row limit. One known gap remains open: the translation step sometimes caps its own query at 100 rows, so for a “list everything” question, check the query shown beside the answer.

Does it know every system in our landscape?

It knows a defined list of 18 systems and 4 business streams. Anything outside that list is not recognised until it is added. This is a deliberate choice: a fixed list cannot mistake a random word for a system.

Can someone, or an AI agent, change or delete our data through it?

No. Queries run in a read-only mode enforced by the database itself, not merely by the application, so a query that tries to write is refused.

Is our information sent outside?

The graph and its database run locally. To turn an English question into a query, the question and a description of the graph’s structure (the kinds of thing and link, and names such as the system list) are sent to Claude. The query then runs locally.

What if two documents contradict each other?

The graph records what each document mentions; it does not decide who is right. The Evidence Agent reads the passages, and when sources disagree it reports the answer as conflicted rather than picking one silently.

Who checks the checks?

The checks themselves are covered by automated tests, and the answer key for the question check is reviewed by people who know the programme. Every check run is kept, so a change in quality over time is visible.

For the team

Running and maintaining the checks

Who — whoever maintains the graph

Everything is available on the Quality view. From the command line, in the repository root:

.venv/bin/python -m backend.graph.graph_eval structure   # check the graph itself
.venv/bin/python -m backend.graph.graph_eval questions   # run the question check (uses Claude)
.venv/bin/python -m backend.graph.graph_eval rescore     # re-compare the last run, no Claude calls
.venv/bin/python backend/tests/test_graph_eval.py         # the checks' own tests
  1. After rebuilding the graph — open the Quality view; the structure check shows at once whether anything moved.
  2. After changing how questions are translated — run the question check and compare with the previous run.
  3. Reviewing the answer key — read each reference query in data/graph_eval_questions.json, correct any that are wrong, set "reviewed": true, then re-score.
  4. Adding a question — add it to the same file with its reference query and how it should be compared (same rows, values found or route length).

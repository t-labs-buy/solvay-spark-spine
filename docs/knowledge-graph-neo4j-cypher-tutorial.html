The knowledge graph, Neo4j and Cypher

How the Solvay SPARK knowledge graph is built from project documents, how it is stored as nodes, labels, relationships and properties in a Neo4j graph database, and how Cypher — written by hand or generated from plain English by Claude — queries it. Written so it can be followed without a graph background, and deep enough to answer the questions an architecture audience will ask.

Audience — architects, developers, functional leads, anyone presenting the platform Database — Neo4j 5.26 Community, with APOC Graph — 11,257 nodes · 20,893 relationships Source of truth — knowledge_graph.json

The whole picture in one page

Who — everyone

Project documents — functional specifications, workshop decks, spreadsheets, meeting minutes — are converted to Markdown. From that Markdown two things are built: a search index of text passages in PostgreSQL, and a knowledge graph of the things the documents talk about (business streams, SAP and third-party systems, BPML process steps, SPARK tickets) and which documents and passages mention which. The graph is written to a JSON file, then loaded into Neo4j, a graph database, where it can be queried with Cypher, Neo4j's query language.

The one sentence to remember

The graph records which documents and passages name which entities, extracted by deterministic rules and traceable to the exact passage. It does not store the documents' text, and it does not claim that two systems are integrated — only that something mentions them.

Part 1 · Storage

Which databases hold what

Who — architects, developers

Three stores are involved. Only one of them is a graph database, and it is deliberately not the source of truth.

StoreTechnologyHoldsRole
Retrieval indexPostgreSQL 18 with the pgvector 0.8.2 extension 217 documents (rag_documents) and 8,867 chunks (rag_chunks): the text, its heading path, a 1,024-dimension bge-m3 embedding and a full-text tsvector What semantic and keyword search read. The agents quote from here.

Why the JSON file stays the source of truth The graph is derived data: it is rebuilt from the documents, deterministically. A file diffs in git, needs no server to read, and lets the app and its tests run with Neo4j switched off. Neo4j adds a query language and a planner; it does not need to be where the truth lives.
What the trade-off costs Two copies of the graph. The Neo4j copy records which build it holds (a fingerprint), is reloaded automatically on start-up and after every rebuild, and the Cypher view says when it is behind — so the copy can lag, briefly, but cannot silently diverge.

Part 2 · Construction

How the knowledge graph is constructed

Who — anyone asked "where do the entities come from?" Code — knowledge_graph.py

Construction is rule-based and deterministic: no language model decides what is an entity or a relationship. The same documents always produce the same graph, node for node, which is what makes it auditable and diffable.

1Convert every document to Markdown

Docling reads each source file — Word, PowerPoint, Excel, PDF, e-mail — and writes Markdown that keeps headings and tables. Pictures are read by a vision model or OCR, and the Markdown records which. Files live per category under solvay-spark/<category>/markdown; the category (DR, PKG, SAP, UNFILED) comes from the folder or the file's own front matter.

2Chunk and index the text

Each Markdown file is split along its headings into chunks of about 500 tokens (the average is 416; the chunker caps a chunk at 1,000 unless a single table row or line is itself longer). Each chunk is embedded with bge-m3 (via Ollama, 1,024 dimensions) and stored in PostgreSQL with its heading path and a full-text vector. Search fuses vector similarity and keyword ranking with reciprocal rank fusion (k = 60). A chunk's id is its category and row id — PKG:10003882 — and that exact id is what the agents cite and what the graph's passage layer uses.

3Lay down the fixed vocabulary

Four business streams and eighteen systems are defined in code, not discovered, each with a description; every system also carries a kind:

kindSystems
sapS4HANA (SAP S/4HANA), EWM, GTS, MDG, SAPTM
legacy_erpECC, WP1, PF1, M3
middlewareCPI (SAP CPI)
third_partySOVOS, ESKER, Elemica, Coface, OMP
crm · sap_ui · portalSalesforce · Fiori · eCommerce (Solvay@eCommerce)

Streams: L2C Lead to Cash, I2D Idea to Delivery, R2R Record to Report, P2P Procure to Pay.

4Build the process hierarchy from the BPML workbook

The BPML hierarchy is read directly from BPML_ProcessesHierarchyExtended.xlsx (its Markdown conversion is too wide to be useful), and the Lead-to-Cash L4 steps from the L1–L4 process register, each carrying its Jira key as jira_key. Every process a document names is chained up to its value chain through SUBPROCESS_OF using the workbook's real parents — codes the workbook does not hold are left without a parent rather than given an invented one.

5Extract entities from every document

For each Markdown file a :Document node is created, and its text — plus its filename, with separators opened into spaces — is matched against four families of patterns: 

# Streams: the code as a whole word
STREAM_RE = {sid: re.compile(r"\b" + sid + r"\b", re.I) for sid in STREAMS}

# Systems: word-bounded so "ADECCO" is not ECC and "ECCN" (an export code) is not either
SYSTEM_RE = {
    "S4HANA": re.compile(r"\bS[/ ]?4[\s/-]?HANA\b|\bS/4\b|\bS4\b", re.I),
    "ECC":    re.compile(r"\bECC\b", re.I),
    "SOVOS":  re.compile(r"\bsovos\b", re.I),
    "CPI":    re.compile(r"\bCPI\b"),           # short acronyms stay case-sensitive
    # ... 18 in all
}

# BPML dash codes (O-020-090), guarded so INT-P-080-160 is not read as P-080-160
CODE_RE = re.compile(r"(?<![A-Za-z0-9-])([A-Za-z][A-Za-z0-9]{0,3})-(\d{2,3}(?:-\d{2,3})+)\b")

# SPARK tickets, in the body or the filename
TICKET_RE = re.compile(r"\bSPARK[-_ ]?(\d{4,6})\b", re.I)

6Record the evidence on every relationship

A link from a document is not just asserted; it carries how it was made and where: 

{
  "source": "doc:SPARK_FS_L2C_SPARK -22234-FS_Interface - SOVOS_docx.md",
  "target": "system:SOVOS",
  "relation": "mentions_system",
  "method": "name_match",
  "mentions": 20,
  "chunk_count": 8,
  "chunks": ["PKG:10003878", "PKG:10003880", "PKG:10003881", "PKG:10003882", "PKG:10003883"]
}

method is the rule, mentions how often the document names the target, chunk_count how many of its passages do, and chunks the first five of those passage ids — so a graph fact can be opened as the sentence it came from.

7Add the passage layer

Every indexed chunk becomes a :Chunk node, linked from its document with HAS_CHUNK and to each entity it names with MENTIONS {count} — the standard graph-RAG shape. Chunks are read from the retrieval index rather than re-chunked, so a chunk node's chunk_key is exactly the id retrieval returns. A chunk mention is kept only where the document itself is linked to that entity, so the passage layer never asserts something the entity layer does not.

8Fingerprint, sort and cache

Nodes and edges are emitted in sorted order, so two builds of the same corpus are byte-identical. The build is cached in knowledge_graph.json under a fingerprint of every input: the Markdown files, the BPML workbook and the state of the retrieval index (a re-index renumbers chunk ids). Change any of them and the next read rebuilds the graph, in about eight seconds.

What the graph does not claim

Relationships are co-occurrence: a document names a system. They do not mean the system runs there, or that two systems named together are integrated. No text is stored in the graph and no language model extracted anything, so there are no hallucinated entities — but also no semantics beyond "this is named here". For what a passage says, read the passage (its id is on the relationship).

What you have now

2,390 entities (218 documents, 1,985 processes, 165 specs, 18 systems, 4 streams), 4,789 entity relationships and 8,867 passages with 7,237 mentions — every link traceable to a rule and a passage.

Part 3 · The model

Nodes, labels, relationships and properties

Who — anyone writing a query

Neo4j stores a labelled property graph. A node has one or more labels and any number of properties; a relationship has exactly one type, a direction, a start and an end node, and properties of its own. Property values are strings, numbers, booleans, temporals or lists of those — not nested maps, which is why a chunk's mentions are relationships rather than a map property.

Naming conventions

Neo4j's conventions are followed: labels in PascalCase, relationship types in UPPER_SNAKE_CASE. Properties keep the extractor's snake_case (chunk_count, heading_path), which Cypher is indifferent to.

Why one MENTIONS_SYSTEM instead of runs_on, integrates_with, interfaces_with?

Earlier versions had six system relationship types, but they were chosen by which system was named, never by what the document said — every S/4HANA link was runs_on. A relationship type should carry meaning; the only meaning the extractor has is "names", so there is one type, and the system's kind is a node property.

Where are degree, colour and size?

Not stored. They are presentation: the app computes them when it loads the graph, and Neo4j computes degree itself (COUNT { (n)--() }). Storing degree made it go stale; storing the display radius as size once overwrote each document's file size — now kept as bytes.

Part 4 · Inside Neo4j

How Neo4j stores the graph on disk

Who — architects, database people

Neo4j is a native graph database: nodes and relationships are its storage primitives, not rows joined at query time. The database directory (/data/databases/neo4j) holds a set of store files, each a sequence of fixed-size records addressed by id: 

neostore.nodestore.db                   one record per node: first relationship, first property, labels
neostore.relationshipstore.db           one record per relationship: start, end, type, and the next/previous
                                        relationship of each end node (a doubly linked chain)
neostore.relationshipgroupstore.db      per-type relationship groups for dense nodes (many relationships)
neostore.propertystore.db               property records, chained per node / relationship
neostore.propertystore.db.strings       long string values
neostore.propertystore.db.arrays        list values (e.g. a relationship's chunks)
neostore.labeltokenstore.db(.names)     label names, stored once, referenced by id
neostore.relationshiptypestore.db       relationship type names, stored once
neostore.propertystore.db.index.keys    property key names, stored once
neostore.counts.db                      counts per label and per relationship type, for the planner
schema/index/…                          the indexes behind the uniqueness constraints
Index-free adjacency A node record points at its first relationship, and each relationship points at the next one for each of its two nodes. Following a relationship is pointer-chasing between fixed-size records — its cost depends on the neighbourhood, not on the size of the graph.
Tokens Label, relationship-type and property names are stored once and referenced by small integers. MENTIONS_SYSTEM is written once, not 556 times.
Dense nodes SAP S/4HANA is named by 146 documents. For nodes with many relationships Neo4j groups them by type and direction, so asking for one type does not walk all the others.
Page cache Store files are memory-mapped through a 256 MB page cache; the whole 14 MB store fits, so queries run from memory.

Indexes and constraints

Twelve uniqueness constraints — id on every label, plus the natural key (code, filename, ticket, chunk_key). Each constraint is backed by a RANGE index, which is how a query starts from "the System whose code is SOVOS" without scanning. Two token lookup indexes (one for labels, one for relationship types) come with every Neo4j 5 database and answer "all nodes with label X". (Community Edition has uniqueness constraints; node-key and existence constraints are Enterprise features.) 

SHOW CONSTRAINTS YIELD name, type, labelsOrTypes, properties;
SHOW INDEXES YIELD name, type, labelsOrTypes, properties;

Transactions and durability

Every write is ACID: it goes to the transaction log first (/data/transactions/neo4j), and store files are brought up to date at checkpoints; after a crash Neo4j replays the log from the last checkpoint. Because this database is a copy that is rewritten on every load, the log is rotated at 32 MB and kept to 100 MB.

Why a graph database for this at all

The questions people ask of this data are paths and neighbourhoods: which passages name two systems together, which documents connect a process to a ticket, what sits above a step in the hierarchy. In SQL each hop is a join over a link table; in a graph store each hop is a pointer, and the query looks like the pattern it asks for. At 11,000 nodes either is fast — the gain here is mostly expressiveness, and the planner and tooling that come with it.

Part 5 · Loading

How the graph gets into Neo4j

Code — kg_neo4j_load.py
  1. Expand — property_graph() joins the entity and passage layers and turns each chunk's stored mentions into HAS_CHUNK and MENTIONS relationships.
  2. Batch — nodes are grouped by label, relationships by (source label, type, target label); presentation properties are dropped.
  3. Constrain — the twelve uniqueness constraints are created if missing; they are also the indexes the next steps use.
  4. Replace — everything is deleted, in batches of 5,000, so a node removed from the graph cannot linger.
  5. Write — nodes, then relationships, 2,000 rows per statement.
  6. Record — a single (:_GraphMeta) node stores the build fingerprint, counts and load time.
// constraints first -- they are the indexes the MATCHes below use
CREATE CONSTRAINT system_code IF NOT EXISTS FOR (n:System) REQUIRE n.code IS UNIQUE;

// replace, never merge
MATCH (n) CALL (n) { DETACH DELETE n } IN TRANSACTIONS OF 5000 ROWS;

// nodes, one label per batch
UNWIND $rows AS r CREATE (n:System) SET n = r;

// relationships, both ends found through the id index
UNWIND $rows AS r
MATCH (a:Document {id: r.s}) MATCH (b:System {id: r.t})
CREATE (a)-[x:MENTIONS_SYSTEM]->(b) SET x = r.p;

A full load takes about three seconds. It runs when the app starts (if Neo4j holds an older build), after every graph rebuild, from the Cypher view's Reload into Neo4j button, and from the command line: 

docker compose -f compose.neo4j.yml up -d        # or: podman compose ...
.venv/bin/python -m backend.graph.kg_neo4j_load                # load if stale
.venv/bin/python -m backend.graph.kg_neo4j_load --force        # reload regardless
.venv/bin/python -m backend.graph.kg_neo4j_load --status
Why CREATE and not MERGE

MERGE is "match or create" and is right for incremental updates. This load is a full replacement into an empty database, so every node and relationship is new; CREATE skips the lookup, and the uniqueness constraints would still reject a duplicate.

Part 6 · Cypher

Cypher: querying by drawing the pattern

Who — anyone writing a query Needs first — the model in Part 3

Cypher is Neo4j's declarative query language, and a major influence on the ISO GQL standard. A query describes the shape of what you want in ASCII art, and the database finds every place in the graph that has that shape.

WriteMeans
(d)a node, bound to the variable d
(d:Document)a node with the label Document
(s:System {code: 'SOVOS'})…whose property code equals 'SOVOS'
-[:MENTIONS_SYSTEM]->a relationship of that type, in that direction
-[r:MENTIONS_SYSTEM]->…bound to r, so its properties can be read (r.mentions)
-[:SUBPROCESS_OF*]->one or more hops (variable length); *..4 caps it at four
--a relationship in either direction
$codea parameter, passed separately from the query text

Reading a query, clause by clause

// Which legacy ERP systems do DR documents mention most?
MATCH (d:Document {category: 'DR'})-[r:MENTIONS_SYSTEM]->(s:System {kind: 'legacy_erp'})
RETURN s.code AS code, count(DISTINCT d) AS documents, sum(r.mentions) AS mentions
ORDER BY mentions DESC
  1. MATCH — every path from a DR document, over a MENTIONS_SYSTEM relationship, to a system of kind legacy_erp.
  2. RETURN — per system (the non-aggregated column is the grouping key): the number of distinct documents and the sum of the mentions property on the relationships.
  3. ORDER BY — most-mentioned first. Result: ECC in 47 documents with 198 mentions, then PF1, WP1, M3.

The same question in SQL, for comparison

SELECT s.code, COUNT(DISTINCT d.id) AS documents, SUM(r.mentions) AS mentions
FROM documents d
JOIN document_mentions_system r ON r.document_id = d.id
JOIN systems s ON s.id = r.system_id
WHERE d.category = 'DR' AND s.kind = 'legacy_erp'
GROUP BY s.code
ORDER BY mentions DESC;

For one hop the two are similar. The difference shows with depth: a three-hop pattern is three more joins in SQL and three more arrows in Cypher, and a variable-length path (*) needs a recursive CTE in SQL.

Part 7 · Execution

What Neo4j does with a query

Who — developers, performance questions
  1. Parse — the text becomes a syntax tree; errors here are Neo.ClientError.Statement.SyntaxError.
  2. Plan — the cost-based planner uses the counts store and the indexes to choose where to start and how to expand; plans are cached per query text, which is one reason to use parameters.
  3. Execute — operators pull rows through the plan lazily, so a LIMIT stops work early.

EXPLAIN shows the plan without running the query; PROFILE runs it and counts the work. The real plan for "documents that mention SOVOS":

PROFILE
MATCH (d:Document)-[:MENTIONS_SYSTEM]->(s:System {code: 'SOVOS'})
RETURN d.filename
ProduceResults        d.filename                                      rows 2   db hits 0
  Projection          d.filename AS d.filename                        rows 2   db hits 2
    Filter            d:Document                                      rows 2   db hits 2
      Expand(All)     (s)<-[:MENTIONS_SYSTEM]-(d)                     rows 2   db hits 12
        NodeUniqueIndexSeek  UNIQUE s:System(code) WHERE code = $autostring_0   rows 1   db hits 2

Read it bottom-up: the planner started at the one System whose code is SOVOS, found through the uniqueness index in 2 database hits, then followed its incoming MENTIONS_SYSTEM relationships to 2 documents. It never scanned the 218 documents. (It also turned the literal 'SOVOS' into a parameter, $autostring_0, so the plan is reused for any code.)

What makes a query fast here

Start from something indexed — a code, filename, ticket or chunk_key — and expand outward. A pattern with no anchor (MATCH (a)--(b)) must touch everything; a variable-length path with no upper bound can explode. The app's 20-second timeout and 1,000-row cap exist for exactly those.

Part 8 · Examples

Worked queries on this graph

Who — anyone at the Cypher view

Documents naming SOVOS and SAP CPI, and the passages naming SOVOS

MATCH (d:Document)-[:MENTIONS_SYSTEM]->(:System {code: 'SOVOS'}),
      (d)-[:MENTIONS_SYSTEM]->(:System {code: 'CPI'}),
      (d)-[:HAS_CHUNK]->(c:Chunk)-[:MENTIONS]->(:System {code: 'SOVOS'})
RETURN d.filename AS document, collect(c.chunk_key) AS chunks

Three patterns sharing d must all hold; collect() gathers each document's passages into one list.

Passages that name two systems together

MATCH (d:Document)-[:HAS_CHUNK]->(c:Chunk),
      (c)-[:MENTIONS]->(:System {code: 'S4HANA'}),
      (c)-[:MENTIONS]->(:System {code: 'Salesforce'})
RETURN d.filename AS document, c.chunk_key AS chunk, c.heading_path AS section
LIMIT 25

Same passage, not merely the same document — the passage layer is what makes "discussed together" answerable.

A process step up to its value chain

MATCH p = (:Process {code: '4.10.2.2'})-[:SUBPROCESS_OF*]->(top:Process)
WHERE NOT (top)-[:SUBPROCESS_OF]->()
RETURN [n IN nodes(p) | n.code + ' ' + n.description] AS chain
4.10.2.2 Create & Save Return Order → 4.10.2 Process Returns → 4.10 Manage Customer Complaints → 4.0 Lead to Cash

Primary specifications and the systems they name

MATCH (d:Document)-[:IMPLEMENTS_TICKET]->(t:Spec)
OPTIONAL MATCH (d)-[:MENTIONS_SYSTEM]->(s:System)
RETURN t.ticket AS ticket, d.filename AS document, collect(s.code) AS systems
ORDER BY ticket

Documents citing process codes BPML does not hold

MATCH (d:Document)-[:SPECIFIES_PROCESS]->(p:Process {in_bpml: false})
RETURN p.code AS code, p.description AS description, count(d) AS documents
ORDER BY documents DESC LIMIT 25

The shortest route between two systems

MATCH p = shortestPath((a:System {code: 'eCommerce'})-[:MENTIONS_SYSTEM*..4]-(b:System {code: 'S4HANA'}))
RETURN p

Returns a path (system ← document → system). In Neo4j Browser it is drawn as a graph.

How many relationships each system has, computed by Neo4j

MATCH (s:System)
RETURN s.label AS system, s.kind AS kind, COUNT { (s)<-[:MENTIONS_SYSTEM]-() } AS documents
ORDER BY documents DESC

Read-only, enforced by the database

Every query from the app runs in a READ transaction. Neo4j itself refuses any write inside one — CREATE, MERGE, SET, DELETE all fail with Neo.ClientError.Statement.AccessMode: Writing in read access mode not allowed. This is the database's rule, not a keyword filter that a clever query could slip past. On top of it: at most 1,000 rows are returned, and a query is cancelled after 20 seconds. 

@unit_of_work(timeout=QUERY_TIMEOUT)          # 20 s, enforced server-side
def work(tx):
    result = tx.run(text, params)
    ...

with driver().session(database="neo4j", default_access_mode="READ") as s:
    keys, rows, truncated, summary = s.execute_read(work)
Neo4j Browser is not read-only

The Browser signs in as the admin user and can change the database. That is acceptable only because the database is a disposable copy: the next load replaces it entirely from knowledge_graph.json. Do not treat edits made there as data.

Use parameters, not string formatting

WHERE s.kind = $k with {"k": "middleware"} keeps values out of the query text: no injection, and one cached plan for every value.

Grounded in the real graph

The prompt carries the schema generated from the same batches Neo4j was loaded from: every label with its properties and count, every relationship pattern with its properties, and the exact values a query filters on — S4HANA = SAP S/4HANA (sap), the categories, the relationship methods, the two process-code formats — plus the nine example queries. A model that has to guess a value writes a query that runs and returns nothing; this is why it writes {code: 'S4HANA'}, not 'S/4HANA'. The prompt is cached (Claude prompt caching), so after the first question most of it is not re-billed.

Checked before anything runs

The draft is planned with EXPLAIN inside a READ transaction. The plan's query_type must be r (read-only) — rw, w or s is rejected. A syntax error or a write goes back to Claude, in the same conversation, with Neo4j's own message, and it corrects the query: at most three attempts. A draft that still fails is shown with the reason and is not run.

Honest about the graph's limits

Asked "What does the SOVOS specification say about the digital signature?", the model explains that the graph holds no document text and returns the passages to read instead. A question the graph cannot answer at all ("Who approved the returns process?") gets answerable: false and no query.

Part 12 · Questions

Questions an audience will ask

Who — presenters

Is Neo4j the system of record?

No. The graph is derived from the documents and lives in knowledge_graph.json; Neo4j holds a copy for Cypher, replaced on every rebuild and fingerprinted so a stale copy is visible.

Did an LLM build the graph?

No. Entities and relationships come from deterministic rules: a fixed vocabulary of streams and systems, word-bounded patterns, the BPML workbook and the process register. The same corpus always gives the same graph. An LLM is used only to write queries, and every query it writes is checked by Neo4j and shown to the user.

How accurate is the extraction?

Every link records its rule and the passages that triggered it, so any one can be checked. Known false-positive traps are guarded against in the patterns (customer names containing "ECC", the export-control code "ECCN", Salesforce ids containing "S4", "m3" as a unit) and covered by regression tests. What it cannot do is understand meaning: a document that says "we will not use SOVOS" still mentions SOVOS.

Is this an ontology?

A light one: six node types and eight relationship types with fixed meanings, a controlled vocabulary for streams and systems, and the BPML taxonomy as its hierarchy. It is not OWL/RDF and has no inference rules; it is a labelled property graph.

Why not just use PostgreSQL for the graph?

It could be done with link tables and recursive CTEs. Neo4j gives a query language whose queries look like the patterns being asked about, a cost-based planner for traversals, index-free adjacency for multi-hop paths, and tooling (Browser, APOC, schema visualisation) — for no change to where the truth lives.

How does this relate to vector search and RAG?

They answer different questions. Vector search finds passages similar to a question; the graph answers structural ones (which documents name both X and Y, what sits above a process). They meet at the chunk: a :Chunk node's chunk_key is the id vector search returns, so a graph answer can be read as passages and a retrieved passage can be placed in the graph.

Why are chunks stored separately from the entities in the JSON?

8,867 passages among 2,390 entities would turn every neighbourhood, path and canvas into a list of passages. In the JSON they sit under passages; in Neo4j they are ordinary nodes, because queries there choose their patterns explicitly.

Can users change data through Cypher?

Not from the app: READ transactions, enforced by Neo4j. Neo4j Browser signs in as admin and could, but the copy is replaced on the next load.

What happens when documents are added or changed?

The graph's fingerprint covers every input file, the BPML workbook and the index state. The next read rebuilds the graph (about eight seconds) and the Neo4j copy reloads (about three).

How big can this get?

Today: 11,257 nodes, 20,893 relationships, a 14 MB store. Neo4j handles billions of nodes; the practical limits here are the full-replace load (seconds per ten thousand nodes) and the in-memory JSON used by the app, both comfortable well beyond the current corpus.

Why Community Edition?

One database, uniqueness constraints and the full Cypher language are all this needs. Enterprise adds clustering, role-based access, node-key and existence constraints, and online backup — none required for a local, rebuildable copy.

Can the AI generate a wrong query?

It can misread a question. It cannot produce an invalid or writing query that runs: EXPLAIN rejects both, and the database refuses writes regardless. Misreadings are why the explanation and assumptions are shown, and why the query is always visible and editable.

Why did a question return zero rows?

Usually an interpretation: a filter on section headings for a concept the headings do not name, or a combination that does not occur. Read the assumptions, loosen the query in the editor, or ask for the passages and read them.

Are graph algorithms (PageRank, communities) available?

Not installed. The Neo4j Graph Data Science library could be added to the container; APOC is installed and provides schema and utility procedures.

Is any data sent outside?

Neo4j runs locally and listens on localhost only. Plain-English generation sends the question and the graph's schema and vocabulary (labels, property names, system codes) to the Claude API — not document text or query results.

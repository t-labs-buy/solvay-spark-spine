Fit-Gap Copilot · India customer returns

Opus vs Sonnet: model comparison

Six Fit-Gap Copilot runs on identical inputs, three on Claude Opus and three on Claude Sonnet, to find out why the scores for the India returns process move so much from one run to the next.

Audience — Fit-Gap Copilot owners, L2C and rollout leads Runs — 6, all under the solvay account Date — 5 Oct 2026
Contents
Summary

What the comparison found

Opus scored the India returns process higher and far more consistently than Sonnet. The two models also disagree on one question that drives two of the four scores: whether India’s GST, e-invoice (IRN) and e-way bill rules count as confirmed legal requirements.

Opus is steadier GT alignment 52.5 – 58.8 across three runs, a 6.3-point spread. Sonnet ranged 38.8 – 52.5, a 13.7-point spread.
Opus scores higher Average GT alignment 55.9 on Opus against 47.5 on Sonnet, from the same document, prompt and corpus.
They read the law differently Opus never confirmed a statutory item. Sonnet confirmed 2 – 3 every run, which lifts Localization-adjusted and pins Harmonization near 40.
Not the knowledge graph The earlier 62.5 came from the switch to Sonnet on 2 Oct and Sonnet’s run-to-run variation, not from a graph or corpus change.
The answer to “why do the scores differ so much?”

Mostly the model, and for Sonnet also ordinary run-to-run variation in its 1 – 4 dimension ratings. With the inputs held fixed, changing only the model moved average GT alignment by 8.4 points and average Harmonization by 19.9 points.

Method

How the test was set up

Everything the run reads was held constant so that the model was the only variable. Each run was given a fresh upload session holding the same file, so no run could see another’s working.

Why three runs per model

Six Opus runs on 25 Sep, on one file and one corpus snapshot, already ranged from 46.3 to 58.8. A single run per model could not tell a model difference from ordinary variation. Three each is the minimum that shows a spread; five each would give a firmer answer.

How Localization-adjusted is worked out

Localization-adjusted = GT alignment + (100 − GT alignment) × the materiality-weighted share of deviations that are a confirmed statutory or SAP-delivered localization. A suspected localization does not count. That is why every Opus run shows Localization-adjusted equal to GT alignment: its share was 0%.

Opus looked at the same GST, IRN and e-way bill steps and graded every one of them SUSPECTED. That single difference explains the other two scores:

  1. Localization-adjusted: Sonnet’s sits 15 – 18 points above its GT alignment, Opus’s is equal to it.
  2. Harmonization potential: Sonnet’s is stuck at 38 – 41 because each confirmed item is capped at 15; Opus’s is 58 – 62.
Which model is right here is a human call

Whether IRN, e-way bill and GST reconciliation are confirmed statutory obligations for returns is a legal question. Sonnet based its confirmations on web search results about India e-invoicing. The India tax team should settle it, so that the answer stops changing from one run to the next.

Context

Before this test, eight runs had been made on the same India file. The six on 25 Sep used Opus; the two on 2 Oct used Sonnet, after FITGAP_COPILOT_MODEL in .env was changed. Prompt versions also changed between most of the 25 Sep runs.

Was it because the knowledge graph was updated?

No. The graph call (compare_entities) returned the same result in both periods: “2 shared, 0 new entities”. The only documents added to the corpus after 25 Sep, an ECC interim-process PDF and BPML_Process_xlsx, were not cited by either 2 Oct run. And with the corpus held fixed, the 25 Sep runs still ranged 46.3 – 58.8.

Where did the 62.5 come from?

From ro_0eb213081e, a Sonnet run on 2 Oct. Today’s three Sonnet runs scored 38.8 – 52.5 on the same inputs, so 62.5 sits at the top of a wide Sonnet range rather than reflecting a real change.

Next steps

Recommendations

1Use one model for every country comparison

Scores from different models are not comparable. On these results that model should be Opus: it scores more consistently, at about twice Sonnet’s cost per run.

The app is currently on Sonnet

.env sets FITGAP_COPILOT_MODEL=claude-sonnet-5. Until that changes and the server restarts, new runs from the app will keep showing Sonnet’s spread.

2Let a person decide the statutory status of the India tax items

Record the India tax team’s answer on IRN, e-way bill and GST reconciliation, so it no longer depends on how a model reads web search results in a given run.

3Make the dimension ratings less of a judgement call

Harmonization is already scored by a fixed rule from each deviation’s proposed action. Giving the seven dimension ratings explicit criteria in the same way would shrink the remaining spread. Until then, treat a single run’s GT alignment as accurate to about ±5 points on Opus, and report a spread across a few runs when the number matters.

Limits

Caveats

  1. Small sample: three runs per model shows the direction, not a precise spread. Five each would cost about $22 in total.
  2. One document, one process: the result is for India returns (4.10.2). Another country or process may behave differently.
  3. A restarted process: the two models were started in parallel and collided while setting up the database tables; the first Sonnet process stopped before starting a run and was restarted. No run was lost or affected.
  4. Not committed: the script that ran these lives outside the repository. The six runs are stored in the database and can be opened from the solvay history.

Source of the figures: every number on this page is read from the rollout_runs table for the six run ids listed, plus backend/agents/rollout/scoring.py for how the scores are combined.
